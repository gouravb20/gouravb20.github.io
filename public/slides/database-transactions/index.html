Transactions:
what a commit promises.

A transaction groups reads and writes so they succeed or fail together, and so concurrent transactions don't trip over each other. Four questions sort every database: how much one transaction covers, when a commit is safe, what concurrent transactions see, and how the database enforces it.

one key → any rows fsync → majority of replicas read committed → serializable locks ↔ MVCC ↔ optimistic

TRANSACTIONS / 01

The problem

Two things go wrong: crashes and concurrency

Without transactions, the application has to handle every half-finished write and every race by itself.

PROBLEM 1 · FAILURE

A crash halfway through

A transfer is two writes. The power fails between them: the money has left Alice and never reached Bob.

UPDATE alice SET balance = balance − 100 ✓
⚡ power fails
UPDATE bob   SET balance = balance + 100 never runs
→ $100 has vanished
PROBLEM 2 · CONCURRENCY

Two clerks, one seat

Both check the last seat at the same moment, both see it free, both sell it. Each step was correct on its own.

clerk A seats left? → 1 ········ sell ✓
clerk B ··· seats left? → 1 ··· sell ✓

→ two tickets for one seat

A transaction gives you · all or nothingIf anything fails before the commit, the database discards every write of the transaction. After a crash you find all of it or none of it.

A transaction gives you · isolationAt the strictest isolation level (serializable), concurrent transactions behave as if they ran one after another. Weaker levels let some races through, and most databases default to one of them.

Read more: DDIA (1st ed.) ch. 7, Transactions

THE PROBLEM / 02

ACID, unpacked

Four letters, four different promises

The acronym (Härder and Reuter, 1983) bundles guarantees that come from different parts of the database, and one that doesn't come from the database at all.

A

Atomicity

really: abortability

If a transaction fails partway (a crash, an error, a broken constraint, a deadlock), all of its writes are undone. It is about failure, not about concurrency.

C

Consistency

really: your invariants

Balances add up; every order has a customer. The application defines these rules. The database checks the ones you declare (UNIQUE, FOREIGN KEY, CHECK); serializable isolation protects the rest.

I

Isolation

really: a level you pick

Concurrent transactions shouldn't see each other's half-done work. How strong that is depends on the isolation level, from read committed to serializable.

D

Durability

really: fsync and replicas

A committed write survives a crash, as far as the log flush and the number of replicas allow. Some defaults acknowledge before anything is on disk.

"ACID" on the box doesn't name the isolation level. PostgreSQL, Oracle and SQL Server default to read committed; MySQL InnoDB to repeatable read; SQLite and CockroachDB to serializable. Check the default, not the strongest level on offer.

SCOPE / 05

Axis 02 · atomicity & durability

The log makes a commit atomic and durable

Write-ahead logging: describe every change in an append-only log. A change's log record reaches disk before its data page does, and the commit record before "committed". The pages can follow later.

durable after step 2 · the pages can wait

recovery
ARIES (1992): find the unfinished transactions, redo every logged change missing from disk (theirs too), then undo theirs, since their pages may already be on disk, logging each undo step so a second crash can't repeat work.
group commit
commits that arrive during a flush share the next one, so one fsync covers many transactions. PostgreSQL and InnoDB do it automatically.
PostgreSQL
redo only. An abort just marks the transaction aborted; its row versions stay in the table, invisible, until VACUUM removes them.
InnoDB
a redo log for crashes, plus undo logs that roll changes back and rebuild older row versions for readers.
LSM engines
the same log in front of the memtable, though by default not fsynced per write: RocksDB's WAL (unless sync=true), Cassandra's commit log (every 10 s, slide 07). Part 1 · how an LSM-tree works

A commit is only as safe as its copies. An fsync survives a power cut but not a dead disk or machine. Synchronous standbys (PostgreSQL), semi-sync replicas (MySQL) or a majority write concern (MongoDB) survive losing a machine.

DURABILITY / 07

Axis 03 · anomalies

Six things concurrency can break

Two transactions, T1 and T2, run at the same time; time flows left to right. Each schedule below is a bug. Every level forbids the first; each of the other five slips through at some level.

Dirty write P0

T2 overwrites a value T1 hasn't committed. The rows end up half T1's, half T2's.

T1 x=1 ············ y=1 ✓
T2 ···· x=2 y=2 ✓
→ x=2, y=1: the rule x = y breaks

Dirty read P1

T2 reads T1's uncommitted write, and T1 then rolls back.

T1 x=50 ············ abort
T2 ····· read x → 50
→ T2 used a value that never existed

Read skew A5A

T1 sees x before and y after T2's transfer. A non-repeatable read is the special case where x and y are one row.

T1 read x → 50 ······ read y → 10
T2 ······· x=90 y=10 ✓
→ T1 counts 60, not 100

Lost update P4

Two read-modify-write cycles race; the later write erases the earlier one.

T1 read x → 100 ········ x=130 ✓
T2 ··· read x → 100 x=120 ✓
→ T2's +20 is gone

Write skew A5B

Both check the same rule, then write different rows. Alice and Bob are the only doctors on call.

T1 on call? → 2 ····· Alice off ✓
T2 ··· on call? → 2 ··· Bob off ✓
→ nobody is on call

Phantom P3

T2 inserts a row that matches T1's search. Locking the rows T1 saw can't stop it: the row didn't exist.

T1 count(active) → 10 ··· → 11
T2 ······ insert active ✓
→ T1's search changed under it

Codes from Berenson et al., A Critique of ANSI SQL Isolation Levels (1995). The doctors example is from Cahill et al. (2008), popularized by DDIA (1st ed.) ch. 7.

Single-node baselines

  • PostgreSQL: default Read Committed; Read Uncommitted behaves the same. Repeatable Read is snapshot isolation; Serializable is SSI (slide 15).
  • MySQL InnoDB: default Repeatable Read. Plain SELECTs read a snapshot; UPDATE, DELETE and locking reads act on the latest rows, with next-key locks.

✓ prevented · ✗ possible. * except MySQL InnoDB's Repeatable Read, and TiDB's in its default pessimistic mode, which don't detect lost updates. Lock-based REPEATABLE READ (SQL Server) is a different level: phantoms possible, write skew on rows already read blocked (slide 11). † a snapshot hides rows inserted later, but two transactions can each see no matching row, both insert, and both commit: write skew through a phantom. Last row: on one server every level sees commits that finished before it started; stale reads come from replicas and clocks.

Three words, often confused. Serializability is about transactions over many objects; linearizability is about one object acting like a single up-to-date copy; strict serializability is both. Part 2 · serializable ≠ strict

RR ≠ RR / 11

Axis 04 · concurrency control

Four ways to keep transactions apart

The isolation level says what must not happen. Concurrency control is how the engine stops it, and each way has its own price.

01 · SERIAL

Run one at a time

One thread per partition executes whole transactions, usually stored procedures, back to back. No locks, no conflicts.

VoltDB · Redis

Cost: one core per partition; one slow transaction stalls the rest.

02 · LOCKING

Two-phase locking

Shared locks to read, exclusive locks to write, all held until commit. Conflicting transactions wait.

MySQL and SQL Server SERIALIZABLE · Spanner serializable read-write transactions (default mode)

Cost: waits and deadlocks; readers and writers block each other.

03 · SNAPSHOTS

MVCC

Writers add new row versions; each reader sees a consistent snapshot. Readers don't block writers, and writers don't block readers.

PostgreSQL · InnoDB · Oracle · WiredTiger (MongoDB)

Cost: old versions to clean up; on its own it allows write skew.

04 · OPTIMISTIC

Check at commit

Run without blocking read locks (SSI, OCC), track what each transaction touches, and abort one whose commit would conflict.

PostgreSQL SERIALIZABLE · FoundationDB · CockroachDB (plus write locks) · Aurora DSQL (write conflicts only)

Cost: aborts and retries, which grow with contention.

Real engines combine them. PostgreSQL and InnoDB read through MVCC but still lock the rows they write; SSI is MVCC plus conflict tracking; Spanner's serializable read-write transactions lock by default, and its snapshot reads take no locks.

Read more: DDIA (1st ed.) ch. 7, serializability · Database Internals ch. 5, concurrency control

CONCURRENCY CONTROL / 12

Axis 04 · MVCC

MVCC: readers see a snapshot, writers add versions

PostgreSQL: xmin = created by · xmax = deleted by

  • Visibility rule: I see a version if the transaction that created it had committed when my snapshot was taken, and the one that deleted it had not.
  • No read locks: a reader never waits for a writer, and a long report never blocks updates.
  • Writers still lock: two transactions updating the same row still queue, or one aborts.
  • When the snapshot is taken: per statement under read committed; per transaction under snapshot isolation.

New version in the table

An UPDATE writes a whole new row version next to the old one. VACUUM removes dead versions later.

PostgreSQL

Update in place + undo

The row changes in place; older versions are rebuilt from the undo log. InnoDB does this in the clustered index only: secondary-index entries are delete-marked, then purged.

InnoDB · Oracle

A separate version store

Row versions for RCSI and SNAPSHOT go to tempdb, or into the database itself with Accelerated Database Recovery.

SQL Server

The cost: long transactions hold back cleanup. An open transaction, even an idle one, keeps every version it might read: PostgreSQL tables bloat and InnoDB's history list grows. Oracle reuses old undo instead, so a long query can fail with ORA-01555 "snapshot too old".

MVCC / 13

Axis 04 · locking

Locks: wait for the other transaction

Even MVCC engines lock rows they write. Lock-based SERIALIZABLE also locks what it reads, key ranges included.

Shared and exclusive

S to read, X to write. Many readers may share a row; a writer needs it alone.

held → asked ↓SX
S✓wait
Xwaitwait

Two-phase locking: never take a lock after releasing one. Databases use the strict form: release none until commit or abort.

Locking ranges, not just rows

To stop phantoms, lock the gaps between index entries too: InnoDB's next-key locks, SQL Server's key-range locks.

index   10 ···· 20 ···· 30
scan 15–25 [10 ···· 20 ···· 30]
INSERT 17 → waits until commit

A lookup of one row by a unique key locks only that row.

Deadlocks

The engine aborts one. InnoDB checks when a transaction must wait and rolls back the smaller one (error 1213). PostgreSQL first waits deadlock_timeout (1 s), then checks (40P01).

Ask for a lock in SQLSELECT … FOR UPDATE locks rows as if updating them; FOR SHARE lets others read but not change them. NOWAIT fails at once; SKIP LOCKED skips locked rows (job queues).

EscalationSQL Server turns row locks into a table lock once one statement holds about 5,000 on a table; its deadlock victim gets error 1205. InnoDB and PostgreSQL never escalate row locks.

LOCKING / 14

Axis 04 · serializable snapshot isolation

SSI: run optimistically, abort the dangerous ones

Snapshot isolation plus bookkeeping. Nobody waits for a read; instead, the engine watches for the one pattern that every snapshot anomaly contains.

  1. Read a snapshot, exactly as under snapshot isolation.
  2. Remember what each transaction read: PostgreSQL's SIRead locks, which never block anyone.
  3. Record an rw-dependency when a transaction writes something a concurrent one read: an edge from the reader to the writer.
  4. Abort on a dangerous structure: a transaction with an rw edge in and an rw edge out. The victim fails with 40001; the application retries it.

the doctors from slide 08 · the first to commit wins, the other gets 40001

False positivesIt checks for the pattern, not a full cycle, so some aborts weren't needed. Read tracking coarsens from rows to pages to tables when memory runs short, and a sequential scan marks the whole table.

Read-only, never abortsSERIALIZABLE READ ONLY DEFERRABLE waits for a safe snapshot, then runs with no tracking and can't fail: good for long reports and pg_dump.

Where it comes fromCahill, Röhm and Fekete (SIGMOD 2008). First shipped in PostgreSQL 9.1 (2011), described by Ports and Grittner (VLDB 2012).

ISOLATION BY DB / 17

In the application

When the isolation level isn't enough

Most code runs at the default level. These patterns close the gaps it leaves.

Let the database add it up

UPDATE … SET n = n + 1, MongoDB $inc, Redis INCR. No read-modify-write in the app, so no update to lose.

Lock what you read

SELECT … FOR UPDATE, then write. Every writer of that row must lock it the same way: a plain SELECT never waits. The fix for lost updates under MySQL's Repeatable Read.

Check a version on write

UPDATE … WHERE id = ? AND version = ?; zero rows means someone won, so re-read and retry. Built in: DynamoDB conditions, Redis WATCH, Cassandra IF.

Retry the whole transaction

On 40001 and 40P01 (PostgreSQL), 1213 (MySQL deadlock), 1020 (MariaDB snapshot conflict), 1205 and 3960 (SQL Server deadlock, snapshot conflict). Re-run the logic, not the failed statement, and make it safe to repeat.

Materialize the conflict

Write skew on rows that don't exist yet, like bookings? Create one row per room and time slot, and lock it. A last resort.

Keep transactions short

No user think-time or remote calls inside. Long ones hold locks, block cleanup and abort more; Aurora DSQL stops them at 5 minutes.

Last line of defence: constraints. UNIQUE, FOREIGN KEY and PostgreSQL's EXCLUDE USING gist (no two bookings overlap) hold at every isolation level. A CHECK sees one row only, so it can't stop the on-call write skew.

IN THE APP / 18

Payoff

Myths to drop, questions to ask

Myth-busters

  • ACID ≠ serializable: most defaults are read committed or snapshot.
  • RR ≠ RR: ANSI, MySQL, MariaDB and PostgreSQL mean different things (slide 11).
  • Snapshot isolation ≠ serializable: write skew gets through, Oracle's "SERIALIZABLE" included.
  • MVCC ≠ no locks: readers don't block, but writers still lock the rows they change.
  • NoSQL ≠ no transactions: MongoDB, DynamoDB, Aerospike and Firestore all run multi-item ACID transactions.
  • Commit ≠ durable: Redis's AOF is off by default; Cassandra fsyncs its commit log every 10 s.

Ask any database

  1. What is the default isolation level, not the strongest one?
  2. What is the strongest, and what does it cost: waits, aborts, throughput?
  3. What does a commit wait for: memory, a local fsync, a majority of replicas?
  4. What aborts, with which error, and is it safe to retry?
  5. How long and how big may one transaction be?
  6. Which anomalies must my application prevent by itself?
