ROW vs COLUMNAR / 03

Why columnar wins

Three techniques that compound

1 · Compression

One column holds one type in a narrow range, so it compresses far better than mixed rows. Dictionary (strings → small ints), RLE (value, count), delta / frame-of-reference, bit-packing.

2 · Vectorized execution

Operators process batches (often 1k–4k values) instead of one row at a time: fewer calls per value, SIMD-friendly loops, data that stays in CPU cache. Some engines compile the pipeline to machine code instead.

3 · Data skipping

Each file or block keeps min/max stats (zone maps). WHERE ts >= '2026-09-01' skips whole blocks unread. A good sort / clustering key makes pruning far more effective.

What you pay

Point updates are expensive (one row touches every column file), row reconstruction costs extra when you select many columns, and single-row inserts are inefficient, so writes are batched.

How engines cope

Buffer writes, flush to immutable columnar files, merge in the background: LSM thinking applied to columns. ClickHouse MergeTree parts, Snowflake micro-partitions, Parquet files in a lakehouse.

COLUMNAR / 04

Architecture · warehouse

Warehouses keep state in object storage and rent compute

  • One copy of data as immutable columnar files on object storage: cheap, durable, effectively unlimited.
  • Many compute clusters, stateless and elastic, one per workload, so BI and ELT never fight over the same CPUs. Pause compute and you stop paying for it.
  • A metadata layer tracks which files make up each table, per-file stats for pruning, and the transaction log that gives snapshots and time travel.
  • The cost: cold reads cross the network, so engines lean on local SSD caches, result caches and aggressive pruning.

Where it came from

A data lake was just files in a bucket: cheap and open, but no transactions, no schema enforcement, no reliable concurrent writes. Table formats added the warehouse features on top of those files; the name “lakehouse” was popularized by Databricks.

What you take on

Picking and running a catalog, compacting small files, expiring old snapshots, and accepting that performance features (caching, clustering, indexes) differ per engine.

OLAP ENGINES / 07

Vector databases · 1 of 5

Searching by meaning, not by value

  • Embeddings: a model turns text, images or audio into a vector of a few hundred to a few thousand floats (commonly 384–3072). Similar meaning → nearby vectors.
  • The query is “nearest neighbours”: embed the question, return the k closest stored vectors. No exact match, no WHERE; results are ranked by distance.
  • Distance metric: cosine (angle), dot product (equals cosine on normalized vectors) or Euclidean L2. Use the one your embedding model was trained for.
  • Why B-Trees don't help: they order data along one key; “closest in 768 dimensions” has no sort order. Space-partitioning trees (k-d trees) degrade toward brute force as dimensions grow.
  • Brute force is O(N·d): 10M vectors × 768 dims ≈ 7.7 billion multiply-adds per query. Hence approximate nearest-neighbour (ANN) indexes.

VECTORS · INDEXES / 09

Vector databases · 3 of 5

HNSW: a skip list made of graphs

Hierarchical Navigable Small World: the default index in pgvector, Qdrant, Weaviate and Milvus.

  • Small-world graph: each vector links to its nearest neighbours; greedy routing (hop to the neighbour closest to the query) reaches the right region in few hops.
  • Layers: every vector is on L0; each also appears higher up with exponentially falling probability, like a skip list. Upper layers are sparse express lanes.
  • Search: from the top entry point, hop greedily until no neighbour is closer, drop a layer, repeat. On L0, beam-search keeping the efSearch best candidates; return the top k.
  • Insert: draw the vector's top layer at random, find neighbours with the same search (efConstruction), link to M per layer, prune over-full neighbours.
  • Costs: graph and vectors usually live in RAM; deletes leave tombstones; heavy filters can cut the graph into unreachable pieces.

The hard part is filtering

WHERE tenant = 7 plus nearest-neighbour. Post-filtering can return fewer than k results; pre-filtering can break HNSW's graph connectivity. Engines differ a lot here, so test with your real filters.

Rule of thumb

Already on Postgres with up to a few million vectors: start with pgvector. Very large collections, heavy filtering or strict latency at high QPS: evaluate a dedicated engine.

VECTORS · LANDSCAPE / 12

Time-series · storage tricks

Append-mostly data indexed by time

Workload traits

Writes are almost all appends at “now”; reads are recent windows and rollups; old data is rarely edited and usually expires. Model: (metric, labels, timestamp, value).

Cardinality is the real enemy. Every unique label combination is a separate series; a label like user_id can multiply series until memory and index size blow up.

Standard techniques

Time partitioning into chunks, so expiry is “drop a chunk”. Downsampling / rollups for old data (1s → 1m → 1h). Retention policies as first-class config. Specialized compression, below.

// delta-of-delta timestamps (the idea behind Facebook's Gorilla paper) timestamps : 1000 1060 1120 1180 1241 deltas : 60 60 60 61 delta-of-delta : 0 0 1 ← regular scrapes become mostly zeros → a few bits each // float values: XOR with the previous value; similar values share leading/trailing zero bits v[n] XOR v[n-1] → store only the meaningful middle bits

Regular intervals and slowly changing values are what make these encodings effective; noisy, irregular data compresses much worse.

TIME-SERIES · LANDSCAPE / 14

Also specialized

Graph and search engines

Graph · Neo4j, JanusGraph, Amazon Neptune

Core idea: relationships are stored as direct pointers between nodes (index-free adjacency in native graph stores), so a traversal costs roughly what it visits, not the size of the table.

Wins: multi-hop queries (fraud rings, recommendations, dependency graphs) that become many self-joins in SQL. Watch out: supernodes, and sharding a graph without cutting too many edges.

Search · Elasticsearch, OpenSearch, Solr

Core idea: an inverted index maps each term to the documents containing it; ranking uses relevance scoring such as BM25. Segments are immutable and merged in the background, an LSM-like pattern.

Wins: full-text relevance, faceting, fuzzy matching, log search. Watch out: near-real-time visibility, and it is a poor system of record.

Pattern: each family reorganizes data around the access path it serves, and pays for it in general-purpose behaviour.

Summary · end of Part 2

What to remember.

Layout follows access

Scans over few columns favour columnar storage, compression, vectorization and data skipping.

Lakehouse = warehouse

Same architecture: columnar files, metadata, elastic compute. Only the format and ownership are open.

Vectors need ANN

HNSW is a skip list of graphs; efSearch trades recall for latency.

Specialize deliberately

Start from the dominant query, then check what the specialized engine makes you give up.
