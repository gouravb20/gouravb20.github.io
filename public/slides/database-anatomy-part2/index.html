ROW vs COLUMNAR / 03

Why columnar wins

Three techniques that compound

1 · Compression

One column holds one type in a narrow range, so it compresses far better than mixed rows. Dictionary (strings → small ints), RLE (value, count), delta / frame-of-reference, bit-packing.

2 · Vectorized execution

Operators process batches of values (MonetDB/X100: about 1,000; DuckDB: 2,048) instead of one row at a time: fewer calls per value, SIMD-friendly loops, data that stays in CPU cache. Some engines compile the pipeline to machine code instead. Slide 06 →

3 · Data skipping

Each file or block keeps min/max stats (zone maps). WHERE ts >= '2026-09-01' skips whole blocks unread. A good sort / clustering key makes pruning far more effective. Slide 05 →

What you pay

Point updates are expensive (one row touches every column file), row reconstruction costs extra when you select many columns, and single-row inserts are inefficient, so writes are batched.

How engines cope

Buffer writes, flush to immutable columnar files, merge in the background: LSM thinking applied to columns. ClickHouse MergeTree parts, Snowflake micro-partitions, Parquet files in a lakehouse.

COLUMNAR / 04

Storage · data skipping

The fastest read is the one you skip

Before reading any data, the engine checks metadata and rules out every block that cannot match the filter.

  • Partitions: split the table on a column such as the event date. A filter on that column skips whole partitions before anything is read; BigQuery calls this pruning.
  • Zone maps (min/max indexes): every block stores each column's smallest and largest value, and a block whose range cannot match is never read. DuckDB keeps them per row group; Snowflake per micro-partition (50–500 MB uncompressed).
  • Sort or cluster keys keep those ranges narrow. BigQuery sorts storage blocks by up to four clustering columns. If the data is sorted on something else, every block spans a wide range and little is skipped.
  • Parquet: file → row groups → one column chunk per column → pages, with min/max per chunk and per page (the page index). For IDs or emails, ranges are too wide; a bloom filter answers “definitely not here” or “maybe”, never a false no.
  • ClickHouse: a sparse primary index with one entry per granule of up to 8,192 rows, not per row; a binary search over these entries picks the granules to read.

DATA SKIPPING / 05

Execution · one node

Vectorized or compiled: how the CPU runs a query

Same plan, Scan → Filter → Sum. What changes is how much work one function call does.

  • Volcano (iterator) model: every operator has a next() that returns one row. Simple and composable, but each row costs at least one virtual function call per operator, and the compiler cannot turn that into a tight loop.
  • Vectorized (MonetDB/X100, 2005): keep the iterator, but pass a vector of about 1,000 values per call, small enough to stay in CPU cache. Loops over one column suit SIMD: one CPU instruction applied to several values at once. DuckDB (2,048 values, push-based), ClickHouse (whole blocks, plus some JIT-compiled expressions), Meta's Velox and Databricks' Photon work this way.
  • Compiled (HyPer, 2011): generate machine code per query with LLVM and fuse the operators, so a row stays in CPU registers until a pipeline breaker such as a hash-table build. Umbra, HyPer's successor, and Spark's whole-stage code generation (JVM bytecode) do the same.
  • Neither wins outright: in a like-for-like study, vectorized engines hid memory stalls better, while compiled code needed fewer CPU instructions. Photon chose vectorized because it was easier to build, profile and debug.

push or pull is a separate choice: DuckDB is vectorized and push-based

EXECUTION / 06

Execution · many nodes (MPP)

One query, many nodes: shuffles and joins

MPP, massively parallel processing: slice the table across nodes, run the same plan on every slice, and move as few rows as possible between them.

  • Scatter / gather: a coordinator splits the query into fragments, workers scan their own slices in parallel, and results flow back up. Dremel, BigQuery's engine, began as a tree of root, intermediate and leaf servers.
  • Partial, then final aggregation: each worker pre-aggregates its rows, the partials are hash-repartitioned by group key, and a final step merges them. Only small partials cross the network; Trino's EXPLAIN shows exactly these steps.
  • Broadcast or shuffle join: copy a small table to every node and leave the big one in place, or hash-repartition both sides on the join key. Spark broadcasts tables estimated under 10 MB by default; BigQuery starts with a shuffle and switches to broadcast at run time if one side turns out small.
  • Co-located joins need no move: distribute fact and dimension on the same join key (Redshift DISTSTYLE KEY, or co-location in Citus, which is shared-nothing) and matching rows already sit on one node. Small dimensions are copied to every node (Redshift ALL, Citus reference tables).
  • The shuffle is the bill; skew is the trap: moving rows can dominate a query's cost; BigQuery even runs its shuffles on a separate in-memory tier. One hot key sends most rows to one node and the query waits for it; Spark's adaptive execution can split skewed partitions.

partial agg → repartition → final agg → gather, as in Trino's EXPLAIN

MPP / 07

Modeling

Star schemas: facts, dimensions and when to flatten

Analytical schemas are shaped for scans and group-bys, not for updating one row at a time.

  • Fact table: one row per business event (a sale, a click) with numeric measures and a foreign key to each dimension. It is long and narrow, and it is what you aggregate. Declare the grain first: decide exactly what one row means (one order line? one daily balance?).
  • Dimension tables: wide, flat and denormalized: the text you filter and group by (product name, region, month). A fact table joined to its dimensions by keys is a star schema.
  • Snowflake schema: dimensions normalized into chains of smaller tables. Same information, more joins; Kimball recommends flattening them.
  • Flatten further, or nest: pre-joining facts and dimensions into one wide table removes joins at query time but moves the work to load time (ClickHouse's advice for low latency). BigQuery recommends nested and repeated fields instead: an order keeps its line items inside its row, so there is no join and no shuffle.
  • History, only if you need it: a type 2 slowly changing dimension adds a new dimension row with validity dates when a customer moves, so old facts keep the old address.

STAR SCHEMA / 08

Architecture · warehouse · compute over a storage service

Warehouses keep one shared copy of data and rent compute

  • One copy of data as immutable columnar files on object storage that every compute node can read: cheap, durable, effectively unlimited.
  • Many compute clusters, one per workload, so BI and ELT never fight over the same CPUs. They own no data, only caches, so you can resize them freely, or pause them and stop paying.
  • A metadata layer tracks which files make up each table, per-file stats for pruning, and the transaction log that gives snapshots and time travel.
  • The cost: cold reads cross the network, so engines lean on local SSD caches, result caches and aggressive pruning. A cache is a disposable copy, not a partition: losing a node loses no data.

Where it came from

A data lake was just files in a bucket: cheap and open, but no transactions and no schema enforcement. Table formats added those on top; Databricks popularized the name.

What you take on

LAKEHOUSE / 10

Lakehouse · open table formats

Iceberg, Delta Lake and Hudi: ACID on object storage

A bucket of immutable files gets transactions from a tree of metadata files and one atomic step per commit.

  • Commit = one atomic swap: files are never changed in place. A change writes new data files and a new metadata file, then the table's pointer moves to it in one step; readers see the old snapshot or the new one, never half of each.
  • The metadata tree (Iceberg spec v1–v3): metadata → snapshot → manifest list → manifests with per-file min/max → Parquet files. Unchanged manifests are shared between snapshots. Spec v4, still in development, replaces the manifest list with one root manifest.
  • Optimistic concurrency: writers prepare files without locks and commit only if the table is still at the snapshot they read. On a conflict the Iceberg REST catalog answers 409 and the writer retries. Delta Lake writers race to create the next numbered log file instead; Hudi records each action on a timeline.
  • Copy-on-write or merge-on-read: rewrite the affected files on every update (fast reads), or write changes to small log or delete files that are merged at read time until compaction (fast writes). Hudi offers both as table types.
  • Upkeep and catalogs: time travel works until old snapshots are expired; frequent small commits leave many small files for compaction to rewrite. Iceberg REST catalogs include Apache Polaris (a top-level Apache project since February 2026), Unity Catalog and AWS Glue.

TABLE FORMATS / 11

Real-time OLAP

Fresh and fast: rollups, materialized views and pre-aggregation

Dashboards that must show the last few seconds, answer in under a second, and serve many users at once.

  • Aggregate on the way in: ingest from Kafka continuously and compute summaries at write time, so a dashboard reads a small table instead of scanning raw events. The cost moves from query time to insert time.
  • ClickHouse materialized views are insert triggers: each inserted block runs through the view's query and lands in a target table. An AggregatingMergeTree target stores partial states (sum so far, count so far) that background merges combine, so queries still finish with GROUP BY.
  • Druid rollup (on by default): rows with the same dimensions in the same time bucket become one row with summed metrics. Row counts can drop by orders of magnitude, but single events are gone. Its Kafka ingestion tracks offsets for exactly-once loading.
  • Pinot star-tree index: pre-aggregated rows over chosen dimensions, where a star node aggregates one dimension away. Fast for the group-bys it was configured for, no help for ad hoc ones.
  • Weak points: joins and updates: Druid advises joining before load, and a ClickHouse view with a JOIN fires only on inserts to its left-most table. Updates work within limits: ClickHouse's lightweight UPDATE is meant for up to about 10% of a table; Pinot upserts by primary key at ingest.

OLAP ENGINES / 13

HTAP

One database for both workloads?

HTAP, hybrid transactional/analytical processing: run analytics on the operational database itself, without slowing its transactions.

  • Two requirements: isolation (analytics must not slow transactions) and freshness (analytics must see recent writes). Most designs keep rows for OLTP and add a second, columnar copy for scans.
  • Separate replica: TiDB + TiFlash (Part 1; compute over storage nodes): a columnar copy joins each Raft group as a learner. It receives the log asynchronously and never votes, so it never slows the write quorum, yet analytical reads still see consistent, recent data.
  • Same server, two formats: SQL Server (since 2016) adds an updatable columnstore index to an OLTP table; Oracle Database In-Memory keeps rows in the buffer cache and columns in an in-memory column store; AlloyDB's columnar engine keeps chosen columns in memory, on the primary or on read pool instances.
  • Attached accelerator: MySQL HeatWave: an in-memory columnar cluster beside MySQL; eligible queries are offloaded automatically and changes flow to it in the background. SingleStore is the exception: one format per table, columnstore by default, in-memory rowstore for the hottest tables.
  • What you pay: every write also maintains the column copy, the copy needs memory or nodes, and it covers one source database. Analytics across many systems still needs a warehouse.

CHEAT SHEET / 15

Summary · end of Part 4

What to remember.

Columns, then skip

Store each column on its own and compress it; partitions, sort keys and min/max statistics then decide how much is read at all.

Batches or compiled loops

Both beat one row at a time through the CPU; neither wins everywhere.

Avoid the shuffle

Pre-aggregate locally, broadcast small tables, co-locate big joins on the same key.

Model for scans

Facts at a declared grain, flat dimensions; nest repeated detail instead of joining it.

Table formats are metadata

A lakehouse is a warehouse on open files: a metadata tree over immutable files, committed by one atomic swap in a catalog or one new log file.

Fresh answers cost writes

Real-time engines pre-aggregate on ingest; HTAP systems maintain a second, columnar copy.
