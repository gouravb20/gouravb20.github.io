Distributed OLTP
databases, classified.

One transactional dataset, many machines. Six questions sort every such system: who accepts writes, how the keys are split, who finds the right node, what the nodes agree on, what a transaction promises, and where time comes from.

DISTRIBUTED OLTP / 01

Scoping today

Why distribute an OLTP database?

Three pressures push a database past one machine. DDIA answers with two mechanisms, and real systems almost always use both.

PRESSURE 1

Scale

The data or the write rate outgrows one box. Splitting the keys across machines spreads both.

PRESSURE 2

Survive failures

A copy on another machine keeps serving when a node, a rack or a whole zone dies.

PRESSURE 3

Be near users

Copies in several regions cut read latency, and with the right design, write latency too.

Replication · copies

The same data on several nodes. It raises two questions: who accepts writes, and how stale can a copy be?

DDIA ch 5 · Replication

Partitioning · splits (sharding)

Each node owns a slice of the keys. It raises: how is the key space cut, and who knows where a key lives?

DDIA ch 6 · Partitioning

Out of scope: OLAP engines (ClickHouse, Snowflake, BigQuery) and pure caches. Those are Part 2. ClickHouse comes back once, as an aside on request routing.

THE 6 AXES / 03

Axis 01 · replication

Three ways to accept a write

DDIA's first split: how many nodes may accept a write for the same key, and how the others catch up.

Single-leader

one writer · followers replay its log

No write conflicts. Failover must elect a new leader. Most distributed OLTP, usually one leader per shard.

Multi-leader

a leader per region · async both ways

Local writes everywhere, but two regions can change one row at once. Conflicts must be resolved.

Leaderless

write to N · wait for W · read from R

No failover at all: any replica takes the write. Stale replicas are fixed by read repair and anti-entropy.

DDIA ch 5 · Replicationsync vs async is a separate dial, next slide
REPLICATION / 04

Axis 01 · single-leader

Single-leader means one leader per shard

Almost every distributed OLTP system is single-leader, but per replica group, not per cluster. Leaders spread over all nodes, so writes do too.

3 ranges × 3 replicas · every node leads something

How the followers keep up is a second dial:

async
leader acks at once, ships the log later. Fast; a failover can lose acknowledged writes. Redis Cluster, classic MySQL / Postgres replicas.
semi-sync
wait for one follower to receive the log. MySQL semi-sync, used by Vitess.
quorum
wait for a majority via Raft / Paxos, so no acked write is lost on failover. Spanner, CockroachDB, TiKV, YugabyteDB, DynamoDB, MongoDB with w: majority.

Unit of leadership: Spanner split · CockroachDB range · TiKV region · YugabyteDB tablet · MongoDB replica set per shard · DynamoDB partition · Aerospike partition (master + replicas) · Redis Cluster slot range.

SINGLE-LEADER / 05

Axis 01 · multi-leader

Multi-leader: every region writes

Several nodes accept writes for the same data and replicate to each other asynchronously. You get fast local writes and pay with conflicts.

  • Why: writes in every region without a cross-ocean round trip, offline clients that sync later, collaborative editing.
  • The catch: two leaders can change the same row at the same time, and someone has to pick a winner.
  • Resolving conflicts: last-writer-wins by timestamp (silently drops one write), merge functions or CRDTs, keep both versions for the app, or avoid conflicts by giving each record a home region.
  • Where it shows up: mostly as the cross-region layer. Inside a region, the same systems stay single-leader per shard.
DynamoDB
Global tables (MREC): multi-active, last-writer-wins, the default. The MRSC mode (GA June 2025) gives up that model for strongly consistent reads in every region.
Cosmos DB
Multi-region writes: last-writer-wins by default, or a custom resolution procedure.
Postgres
EDB Postgres Distributed, pgactive: logical replication between primaries (the BDR lineage).
CouchDB
Offline-first sync (PouchDB). Conflicting revisions are kept; a deterministic winner is shown.

Edge case: Galera Cluster and MySQL Group Replication (multi-primary mode) let every node write, but certify each commit against concurrent ones through group communication. Conflicts abort instead of merging, which is closer to synchronous replication than to classic multi-leader.

MULTI-LEADER / 06

Axis 01 · leaderless

Leaderless: quorums instead of a leader

The Dynamo style. A coordinator (any node, or the driver) sends each write to all N replicas of the key and waits for W acks. A read asks R replicas and keeps the newest value.

N · W · R
replicas per key, write acks, read replies. If W + R > N, every read set overlaps the last write set.
read repair
a read that finds a stale replica writes the newer value back to it.
anti-entropy
a background job compares replicas (Merkle trees) and fixes keys nobody reads.
hinted handoff
a live node holds writes for a down replica and replays them later. If those hints count toward W, it's a sloppy quorum.
conflicts
concurrent writes to one key: last-writer-wins per cell by timestamp (Cassandra), or version vectors with siblings (Riak).
CAS
Lightweight transactions (IF …) run Paxos per partition: a linearizable compare-and-set.
Cassandragossip ring · tunable CL
ScyllaDBRaft metadata · tablets
Riakhistoric · version vectors

Myth-buster: Dynamo ≠ DynamoDB. The 2007 Dynamo paper is leaderless. DynamoDB is not: each partition is a Multi-Paxos group with one leader across three availability zones (USENIX ATC 2022 paper).

LEADERLESS / 07

Axis 01 · interactive

Play with N, W and R

Each write lands on W random live replicas; each read asks R random live replicas. Click a replica to take it down.

Press Write, then Read. Try W = 1, R = 1 to see a stale read, then W + R > N to make it impossible.
QUORUM · LIVE / 08

Axis 02 · partitioning

Cutting the key space

How keys map to partitions decides which queries stay on one node and where hot spots form.

Key range

Contiguous, sorted slices. Range scans are cheap; sequential keys (timestamps, auto-increment) pile onto one hot partition. Ranges split as they grow.

Spanner · CockroachDB · TiKV · HBase / Bigtable · MongoDB ranged keys · YugabyteDB range tables · FoundationDB

Hash

hash(key) spreads load evenly; a range query becomes scatter-gather. Often hash on the partition key, sorted within it.

Cassandra / ScyllaDB (token ring) · DynamoDB (partition key + sort key) · MongoDB hashed keys · YugabyteDB default · Citus · Vitess vindexes

Fixed slots

Hash into a fixed, large number of partitions, then assign partitions to nodes. Adding a node moves whole partitions; keys never re-hash.

Redis Cluster 16,384 slots · Aerospike 4,096 partitions · Couchbase 1,024 vBuckets

REBALANCE · A

Move fixed partitions

Aerospike, Redis Cluster, Couchbase.

REBALANCE · B

Split & merge

Ranges split when big or hot: CockroachDB, TiKV, Spanner, HBase, MongoDB chunks.

REBALANCE · C

Per-node tokens

Each node owns many small token ranges (vnodes): Cassandra.

REBALANCE · D

Tablets

Per-table tablets moved one at a time under Raft: ScyllaDB 6.0+.

PARTITIONING / 09

Axis 02 · secondary indexes

Local vs. global secondary indexes

Partitioning by primary key is easy. A query on any other column has to find its partitions somehow.

Local · document-partitioned

Each partition indexes only its own rows. Writes touch one partition; reads by index ask every partition.

MongoDB (queries without the shard key) · Cassandra SAI / 2i · DynamoDB LSIs (within one partition key)

Global · term-partitioned

The index is partitioned by the indexed value. Reads hit one index partition; a write may update index partitions on other nodes.

DynamoDB GSIs (updated asynchronously, eventually consistent) · Spanner, CockroachDB, TiDB, YugabyteDB (the index is just more ranges, updated in the same distributed transaction)

SECONDARY INDEXES / 10

Axis 03 · request routing

Who finds the node that owns the key?

DDIA lists exactly three answers, and your three examples land on one each.

① Any node coordinates

connect anywhere · it forwards

Cassandra, ScyllaDB (coordinator node) · CockroachDB (gateway node) · TiDB, YugabyteDB (any SQL node) · Citus 11+.
Your ClickHouse example works the same way: a Distributed table on any node coordinates. But ClickHouse is OLAP, and SELECTs fan out to all shards unless pruned by the sharding key.

② Routing tier

stateless routers · cached map

MongoDB (mongos + config servers) · Vitess (VTGate + topo server) · DynamoDB (request routers + metadata service) · Spanner front-ends.
Your MongoDB example: yes for a sharded cluster, but mongos is not one central server. You run many stateless ones; the config-server replica set holds the map.

③ Partition-aware client

the driver holds the map · one hop

Aerospike (digest → 1 of 4,096 partitions; client polls the map) · Redis Cluster (slot map; MOVED / ASK redirects) · FoundationDB (location cache) · token-aware Cassandra and shard-aware ScyllaDB drivers.

The lines blur: Cassandra lets any node coordinate, yet token-aware drivers skip that hop. TiDB's SQL nodes are themselves smart clients of TiKV, with a region cache filled from PD.

ROUTING / 11

Axis 03 · partition metadata

Where does the partition map live?

A separate question from routing. A router needs the map; what matters is who owns the true copy and how changes reach everyone.

A · CENTRAL SERVICE

A small cluster that runs consensus

One authority; routers cache it and ask again on a miss.

MongoDB config-server replica set · TiDB PD (embedded etcd, Raft) · YugabyteDB YB-Master (Raft) · Vitess topo (etcd / ZooKeeper / Consul) · HBase (ZooKeeper)

consistent
B · INSIDE THE DATA

Stored as ordinary keys

The map is replicated by the same consensus as user data; no extra service.

CockroachDB meta1 / meta2 ranges (gossip only says where meta1 is) · FoundationDB system keys (\xff) · Bigtable METADATA tablets, Spanner's ancestry

consistent
C · GOSSIPED

Spread peer to peer

No single point of failure, but nodes can disagree for a while, and concurrent topology changes can collide.

Cassandra ≤ 5.0 (token ring + schema) · Redis Cluster (slot map on the cluster bus, config epochs) · Riak

eventually consistent
D · AGREED, THEN EVERYWHERE

A consensus log on every node

Every node holds the agreed map, so every node can route.

ScyllaDB Raft group 0 (schema + topology, default since 6.0) · Cassandra 6 TCM (CEP-21, alpha) · Citus 11+ metadata on all nodes · Aerospike: membership agreed through a principal node; every node then computes the same partition map

consistent

Stale caches are normal. Correctness comes from the owner rejecting a wrong route (MongoDB StaleConfig, TiKV region-epoch / not-leader errors, Redis MOVED) and the router refreshing and retrying.

Axis 05 · transactions

"Supports transactions": up to which rung?

Almost every database supports transactions, but they differ on how far one can reach before atomicity or isolation gives out.

RUNG 1

One key / record

Atomic single-row writes; compare-and-set for read-modify-write.

everyoneCassandra LWT (Paxos)Aerospike SCDynamoDB conditional writes
RUNG 2

One partition / shard

Many keys, as long as they share a partition (or slot, or shard).

Cosmos DB per logical partitionCassandra batch in one partitionRedis MULTI in one slotVitess single-db mode
RUNG 3

Cross-shard, atomic only

Two-phase commit makes it all-or-nothing, but readers on other shards can see half of it ("fractured reads").

Vitess 2PC modeCitus multi-node 2PC
RUNG 4

Cross-shard ACID

Atomic and isolated across shards, via 2PC over Raft/Paxos groups (Spanner, CockroachDB parallel commits, YugabyteDB), Percolator (TiDB), OCC (FoundationDB, Aurora DSQL), or leaderless consensus (Accord).

Isolation levels, by what they prevent

AnomalyRead committedSnapshot ("RR")SerializableStrict serializable
Dirty read / write✓✓✓✓
Read skew✗✓✓✓
Lost update✗✓*✓✓
Write skew · phantoms✗✗✓✓

Single-node baselines

  • PostgreSQL: default Read Committed. Its Repeatable Read is true snapshot isolation; Serializable is SSI (optimistic, aborts dangerous patterns).
  • MySQL InnoDB: default Repeatable Read. Plain SELECTs read a snapshot, but UPDATE and locking reads see the latest rows (next-key locks). *It does not detect lost updates.

Two different words. Serializability is about transactions over many objects. Linearizability is about one object behaving like a single, up-to-date copy. Strict serializability is both. DDIA ch 7 vs ch 9.

ISOLATION BY DB / 17

Axis 05 · serializability

Serializable ≠ strict serializable

Serializable promises some serial order. Strict serializable promises the serial order matches real time.

Three ways to be serializable (DDIA ch 7)

serial
Actually run one at a time per partition: VoltDB, Redis per shard, Calvin-style deterministic ordering.
2PL
Pessimistic locks held to commit: Spanner read-write transactions, MySQL SERIALIZABLE, YugabyteDB.
SSI / OCC
Optimistic: run, then abort on conflict: PostgreSQL SSI, CockroachDB, FoundationDB, Aerospike 8 reads.

Strict: Spanner (external consistency), FoundationDB, Aerospike 8, Cassandra Accord. Serializable, not strict: CockroachDB is linearizable per key, but across unrelated keys clock skew can order transactions against real time.

a stale read that is still "serializable"

STRICT / 18

Axis 06 · clocks

Where do timestamps come from?

MVCC snapshots and transaction ordering need timestamps every node agrees on. Each design pays for that differently.

TrueTime

The clock API returns an interval [earliest, latest], bounded by GPS and atomic clocks (1–7 ms in the 2012 paper). A commit waits out the uncertainty, so timestamp order is real-time order.

Spanner · cost: special hardware + commit wait

Hybrid logical clocks

Physical time plus a logical counter, bumped on every message so causality holds. No special hardware, but clocks must stay within a max offset; reads in the uncertainty window restart.

CockroachDB (500 ms default) · YugabyteDB · MongoDB cluster time

Central oracle

One leader hands out strictly increasing timestamps in batches. Simple and totally ordered, but every transaction pays a round trip to it, which hurts across regions.

TiDB PD TSO (Percolator design) · FoundationDB sequencer

Precise physical clocks

Rely on a tightly synchronized time service instead of an oracle or special hardware in the database.

Aurora DSQL (Amazon Time Sync)

Wall-clock last-writer-wins

Each write carries a timestamp; the highest wins. A node with a fast clock silently discards newer writes (DDIA ch 8).

Cassandra · DynamoDB global tables (MREC)

Version vectors

Don't trust clocks at all: detect that two writes were concurrent and hand both versions (siblings) to the application to merge.

Riak · the Dynamo paper

CLOCKS / 19

Axis 06 · consistency

How stale may a read be, and who chooses?

linearizable
like one copy: a read sees every write that finished before it. Spanner, CockroachDB per key, Cassandra LWT, DynamoDB strongly consistent reads, Aerospike SC.
causal
cause before effect, for everyone. MongoDB causally consistent sessions.
session
read-your-writes and monotonic reads, per client (DDIA ch 5). Cosmos DB Session, the default.
prefix
writes appear in order, maybe late. Cosmos DB consistent prefix.
eventual
replicas converge once writes stop. Cassandra at ONE, DynamoDB default reads, async followers.

The knobs, per system

  • Cassandra / ScyllaDB: consistency level per query: ONE, QUORUM, LOCAL_QUORUM, ALL, SERIAL.
  • MongoDB: write concern (majority by default since 5.0), read concern (local, majority, linearizable, snapshot), read preference.
  • DynamoDB: ConsistentRead on base tables, not on GSIs; global tables choose MREC or MRSC.
  • Cosmos DB: Strong, Bounded staleness, Session, Consistent prefix, Eventual.
  • Spanner / CockroachDB / TiDB: strong by default; opt into stale reads served by followers.

Why no CAP labels? DDIA ch 9: CAP's "C" means only linearizability and network partitions are not optional, so "CA" says little. PACELC is more useful: even with no partition, you trade latency for consistency on every request.

CHEAT SHEET / 22

Payoff

Myths to drop, questions to ask

Myth-busters

  • Dynamo ≠ DynamoDB: DynamoDB has one Paxos leader per partition.
  • Single-leader ≠ bottleneck: one leader per range, spread over every node.
  • mongos ≠ the brain: routers are stateless; the config servers hold the map.
  • Gossip ≠ consensus: gossip converges eventually; Raft and Paxos agree first.
  • RR ≠ RR: MySQL, PostgreSQL and ANSI mean three different things.
  • Distributed transactions ≠ serializable: MongoDB, TiDB and Aurora DSQL are snapshot isolation.
  • 2PC ≠ isolation: Vitess and Citus commit atomically, yet readers can see half a transaction.
  • Serializable ≠ strict: only strict promises real-time order.

Ask any distributed database

  1. Who leads my key, and what happens when it dies?
  2. Where is the partition map, and what happens when my router's copy is stale?
  3. What does a commit wait for: one node, a majority, every region?
  4. Default isolation, maximum isolation, and what the maximum costs.
  5. Can one transaction span shards? Regions?
  6. Where do timestamps come from: TrueTime, HLC, an oracle, wall clocks?
  7. Which reads may be stale, and can I choose per request?
