A database isn't one “type”. It's a set of answers to a few independent questions: what workload it serves, what the application sees, how one machine stores the data, and how many machines share it. Learn the questions, and any new database becomes one row in a table.

DATABASES / 01

The root question · workload

Start with the workload. It picks the layout.

What does a typical query touch: a few whole records, or a few columns of millions of records?

OLTP · online transaction processing

Many small reads and writes by key, from users, in milliseconds: “load order 2”, “add item to cart”. Each query wants a whole record, so a record's fields are stored together: a row layout.

page → [1 Ana NYC 30] [2 Bo SF 12] [3 Cy LA 7]
get order 2 → read one page
row layout · this deck

OLAP · online analytical processing

Few big queries from analysts, scanning millions of rows: “revenue by city this year”. Each query wants a few columns, so each column is stored (and compressed) on its own: a column layout.

id → 1 2 3  · name → Ana Bo Cy
city → NYC SF LA · total → 30 12 7
sum(total) → read one column
column layout · Part 2

HTAP systems serve both, usually as a row store plus a columnar copy (TiDB with TiFlash). Specialized workloads (search, time-series, vectors, graphs) get their own engines in Part 2.

Watch the wording: “wide-column” (Cassandra, Bigtable) is not “columnar”. Wide-column stores keep each row's cells together, so they use a row layout with a flexible set of columns.

THE MAP / 03

Why the axes are independent

Each layer hides the one below it

Codd's 1970 relational paper argued that applications must not depend on how data is organized inside the machine. The ANSI/SPARC model of the mid-1970s named the levels: what users see, the logical schema, the physical storage. Distribution adds one more hidden level: which machine holds the bytes. Because each level is hidden, each can be swapped without the others noticing.

Model ⟂ structure

CockroachDB and TiDB are SQL over an LSM. MongoDB is documents over a B-tree.

Structure ⟂ distribution

RocksDB runs embedded in one process, and the same engine sits under TiKV in a cluster. Distribution is a layer above.

Guarantees ⟂ distribution

SQLite is serializable inside one file. Spanner is strictly serializable across continents.

Model ⟂ architecture

Bigtable is NoSQL, and its servers keep data on a shared file system (Colossus), not on their own disks.

Architecture ⟂ structure

Aurora moves storage to a separate service and still uses B-tree pages.

Mostly independent

Some answers suit each other, so a few combinations recur: the archetypes. The few real dependencies are on slide 22.

INDEPENDENCE / 04

Axis 01 · logical · data model & query

What shape is the data?

Rows in tables, whole documents, values behind keys, or nodes and edges? Asked in SQL, or through an API?

Relational

Rows with typed columns; joins and foreign keys. Asked in SQL.

idnamecity
1AnaNYC

Document

Self-contained JSON-like trees, read and written whole.

{ "_id": 1, "name": "Ana",
  "addr": { "city": "NYC" } }

Key–value

An opaque value behind a key: get, put, delete. The database can't look inside.

user:1 → "…bytes…"

Wide-column

A partition key picks the node; a sort key orders rows inside it. Columns may differ per row.

user#1 │ 2025-01-03 → {…}
user#1 │ 2025-01-07 → {…}

Graph

Vertices and edges with properties; queries walk paths (Cypher, Gremlin). Covered in Part 2.

(Ana)-[:FOLLOWS]->(Bo)

Two sub-questions

Schema: checked by the database on write (relational) or by the app on read (document, key–value).
Query: declarative (SQL says what; the planner picks how) or an API of operations (get, put, find).

What it decidesWhich queries are natural and which hurt (joins, ad-hoc filters, path walks), and how much checking the database does for you.

How to tellThe query language, and the unit of an atomic write: a row, a document, an item. The models converge: Postgres stores JSON; MongoDB has joins.

DATA MODEL / 05

Axis 02 · logical · guarantees

What does a commit promise?

If two clients write at once, or the power fails mid-write, what can the app still assume?

Scope · how much is atomic?

A ladder: one key → one document or row → one partition → any rows on one node → any rows on any node.

  • Memcached: one key.
  • Cassandra: one partition.
  • DynamoDB: up to 100 items.
  • Postgres: any rows; Spanner: any rows, any node.

Isolation · what do others see?

How much concurrent transactions can see of each other's work. Defaults differ:

  • Read Committed: Postgres, SQL Server, Oracle.
  • Repeatable Read: MySQL InnoDB.
  • Serializable: SQLite, CockroachDB.
  • Strict serializable: Spanner.

Durability · when is “OK” safe?

What has happened by the time the database acknowledges a commit:

  • Log flushed to disk: Postgres by default.
  • Flushed every second: Redis AOF's default policy; a crash can lose about a second.
  • On a majority of replicas: MongoDB's default write concern.

What it decidesWhich bugs your application must prevent itself: lost updates, write skew, writes lost in a crash or a failover.

How to tellFind the default isolation level in the docs (not the strongest one offered), and what “commit” waits for: an fsync, a replica, or nothing.

In depth in Part 3: transaction scope · isolation levels · defaults per database · serializable vs strict · Read more: DDIA ch. 7 · Database Internals ch. 5

GUARANTEES / 06

Axis 03 · physical · storage structure

How does a write change the bytes on disk?

Does the engine overwrite data where it lives, or append new versions and merge them later?

B-tree · update in place

  • Walk a sorted tree of pages to the right leaf, change it, write the page back (a write-ahead log makes it crash-safe).
  • Reads: one root-to-leaf path, predictable. Writes: random, and a small change rewrites a whole page.
Postgres · MySQL · SQL Server · Oracle · SQLite · MongoDB · DynamoDB

LSM-tree · append, merge later

  • Buffer writes in a sorted in-memory table, flush it as an immutable sorted file, merge files in the background.
  • Writes: sequential, high throughput. Reads: may check several files; bloom filters skip most.
RocksDB · Cassandra · ScyllaDB · Bigtable · HBase · CockroachDB · TiKV

Also on this axisHeap + indexes (Postgres writes a new row version; VACUUM reclaims the old) · clustered on the key (InnoDB) · copy-on-write B-tree (LMDB) · log + hash index (Bitcask) · hash tables and skiplists (Redis).

What it decidesThe balance of read, write and space amplification. B-trees favour reads; LSM-trees favour writes and usually take less space.

How to tellThe engine's vocabulary: page, vacuum, fill factor point to a B-tree; memtable, SSTable, compaction to an LSM.

Read more: DDIA ch. 3 · Database Internals ch. 2, ch. 6, ch. 7, which frames this axis as three choices: buffering, mutability, ordering.

STORAGE STRUCTURE / 07

Axis 03 · deep dive

How an LSM-Tree works

Log-Structured Merge-Tree: turn random writes into sequential ones, and clean up later.

WAL
every write is appended to a crash-recovery log first.
Memtable
a sorted in-RAM structure (skiplist) absorbs writes.
SSTable
when full, the memtable flushes to an immutable, sorted file on disk.
Compaction
background merge of SSTables into fewer, bigger, sorted levels — drops overwrites & tombstones.
Bloom filter
per-SSTable probabilistic “is the key even here?” to skip files on reads.
Delete
writes a tombstone marker; the value is really removed during compaction.

writes flow down · reads fan across newest → oldest

Trade-off in one line: cheap writes, more work on reads — the mirror image of a B-Tree.

LSM · LIVE / 09

Axis 04 · physical · medium

Where does the data live: memory or disk?

Is RAM the home of the data with disk as a backup, or is disk the home with RAM as a cache?

Disk-first

Data lives in pages on disk; a buffer pool caches hot pages in RAM. The dataset can be far bigger than RAM. Every access goes through the buffer manager: find the page, pin it, latch it, maybe read it from disk.

Postgres · MySQL · Oracle · MongoDB · Cassandra

Memory-first

Data lives in RAM, in structures built for RAM: hash tables, skiplists, pointers. Disk holds only a log and snapshots for recovery, or nothing at all. The dataset must fit in memory.

Redis · Memcached · VoltDB · SQL Server In-Memory OLTP

Hybrid · index in RAM

The index lives in RAM and the records on SSD, so any lookup costs at most one SSD read, without paying RAM prices for the data. Aerospike keeps its primary index in RAM and records on raw SSD; Bitcask keeps a hash of every key in RAM.

Aerospike · Bitcask (Riak)

Why not just add RAM to a disk engine? “OLTP Through the Looking Glass” (SIGMOD 2008) ran one with all its data in memory: most of the time went to buffer management, locking, latching and logging, not useful work. Memory-first engines drop that machinery.

What it decidesLatency and its spread (no disk wait on any read), cost per GB, the largest dataset you can hold, and recovery time: a memory-first restart replays a log back into RAM.

How to tellDoes the sizing guide say RAM ≥ dataset? Is persistence a setting you switch on? Or is there a buffer-pool / cache-size setting to tune?

Read more: Database Internals ch. 1, memory- vs disk-based

MEDIUM / 10

Axis 05 · system · deployment & architecture

Where does it run, and what's shared?

A library in your process, one server, or a cluster? And in a cluster, what do the nodes share?

Embedded

A library linked into the app. No server and no network hop; one process owns the file.

SQLite · RocksDB · LMDB · DuckDB

Single server

Clients connect over the network to one server that owns the disk. Scale up; add replicas for reads.

Postgres · MySQL · SQL Server · Redis

Shared-nothing

Each node has its own CPU, RAM and disk; nodes talk only by messages. Scale out by adding nodes, so the data must be partitioned.

Cassandra · MongoDB · CockroachDB · DynamoDB

Shared storage

Stateless compute over one replicated storage service. Scale compute and storage apart; a new replica or a failover copies no data.

Aurora · Neon · AlloyDB · Bigtable

Landmarks: Stonebraker's “The Case for Shared Nothing” (1986) set the default for scaling out. Aurora (SIGMOD 2017) made shared storage practical: compute ships log records, storage builds the pages. Shared-disk clusters (Oracle RAC) sit in between.

What it decidesHow you scale (up or out), what a failover costs, whether compute and storage can grow separately, and who has to operate it.

How to tellRead the architecture page: one box, boxes that each own a disk, or boxes over a storage service?

Copies and pieces: replication × partitioning

Does each node hold a copy of all the data, a piece of it, or copies of pieces?

Not partitioned · every node has it all
Partitioned · each node has a piece
One copy
one copy · not partitioned

One node

Simplest, and strongly consistent for free. One failure is an outage; one machine is the limit.

SQLite · a lone Postgres
one copy · partitioned

Pieces, no copies

Scales, but losing a node loses its piece. Rare for databases; normal for caches.

Memcached, sharded by the client
Replicated
replicated · not partitioned

Copies of everything

Survives failures and scales reads. Every write still lands on every node, so writes don't scale out.

Postgres + replicas · MongoDB replica set · Redis
replicated · partitioned

Copies of pieces

Each piece lives on several nodes. Scales reads and writes and survives failures; the default for distributed databases.

Cassandra · DynamoDB · Spanner · CockroachDB · TiDB

What it decidesHow far writes scale, what survives a node or a region failing, and what consistency costs: the more copies and pieces, the more the nodes must agree on.

How to tellLook for replica set, replication factor (copies) and shard key, partition key, tablet, region, range (pieces).

ARCHETYPES / 13

Archetype A1 of 7 · embedded engine

Embedded engines

The database is a library. No server and no network: the engine runs inside your process and stores to a local file. Phones, browsers, desktop apps, edge devices, and the storage layer of other databases.

SQLiterelational · B-tree
RocksDBkey–value · LSM
LMDBkey–value · copy-on-write
DuckDBthe OLAP cousin
01Model
Relational (SQLite) or key–value (RocksDB, LMDB)
02Guarantees
Full ACID. SQLite is serializable: one writer at a time
03Structure
B-tree, LSM, or copy-on-write B-tree
04Medium
Disk-first; LMDB maps the file into memory
05Architecture
Embedded: a library in your process
06Distribution
None, by design

Why these answers travel together

No network and one process means nothing to partition or replicate, and simple locking (one writer at a time) buys the strongest isolation cheaply. The result is small, fast and fully ACID.

The exception that proves the axes

Embedded engines are also the bottom layer of distributed databases: TiKV runs RocksDB, YugabyteDB a fork of it, and CockroachDB's Pebble is modelled on it. rqlite and LiteFS replicate SQLite. The engine stays embedded; a system layer above adds distribution.

A1 · EMBEDDED / 14

Archetype A2 of 7 · classic relational server

Classic relational

One server, strong guarantees. Tables, SQL and ACID transactions, with replicas for reads and failover. The 40-year default, and the reason the axes feel inseparable: these answers almost always ship together.

PostgreSQL
MySQL
MariaDB
SQL Server
Oracle
01Model
Relational + SQL; JSON columns too
02Guarantees
Multi-table ACID. Default Read Committed (MySQL: Repeatable Read)
03Structure
B-tree. Postgres keeps rows in a heap; InnoDB clusters them on the primary key
04Medium
Disk-first, hot pages in a buffer pool
05Architecture
Single server

One leader + read replicas; no built-in partitioning

Why these answers travel together

One server owns all the data, so making any set of rows atomic and isolated needs no network round trips and no consensus. That's why transactions, joins and constraints feel like part of “SQL”. The limit is the one server: writes scale up, not out.

The exception that proves the axes

Same engines, other system-layer answers: Citus partitions Postgres across nodes, Vitess shards MySQL, Oracle RAC runs several servers over shared disks, and Aurora moves the storage into a service (archetype A6).

A2 · CLASSIC RELATIONAL / 15

Archetype A3 of 7 · in-memory store

In-memory stores

Data structures over the network. Keys map to strings, hashes, lists, sets, sorted sets and streams, served from RAM in well under a millisecond. Caches, sessions, rate limits, leaderboards, queues.

Redisdata structures · optional persistence
ValkeyLinux Foundation fork of Redis
Memcachedpure cache · no persistence
01Model
Key → data structure (Memcached: key → bytes)
02Guarantees
Each command is atomic; MULTI/EXEC and Lua run as a unit, with no rollback
03Structure
Hash tables, skiplists; no pages
04Medium
Memory-first. Redis can snapshot (RDB) and log (AOF); Memcached never persists
05Architecture
Single server; commands run one at a time
06Distribution
Redis Cluster: 16,384 hash slots, async replicas. Memcached: the client picks the server

Why these answers travel together

With everything in RAM there is no buffer pool and no disk wait, so one thread can run commands one after another: each is atomic without locks. The price: data must fit in memory, and async replication can lose the last writes on a failover.

The exception that proves the axes

Memory-first doesn't mean key–value: VoltDB and SQL Server's In-Memory OLTP are relational. And it doesn't mean “cache only”: Redis with AOF set to fsync on every write is durable, just slower. (Valkey was created in 2024, after Redis changed its license.)

A3 · IN-MEMORY / 16

Archetype A4 of 7 · document store

Document stores

The record is a tree. Each record is a self-contained JSON-like document, loaded and saved whole. A good fit when data is read together (an order with its lines) and the schema changes often.

MongoDBWiredTiger · B-tree
Couchbasememory-first cache
Firestorebuilt on Spanner
01Model
Documents, flexible schema; secondary indexes on any field
02Guarantees
One document is always atomic; MongoDB has multi-document transactions since 4.0
03Structure
B-tree (MongoDB's WiredTiger)
04Medium
Disk-first (Couchbase: memory-first with a managed cache)
05Architecture
Shared-nothing cluster (Firestore: fully managed)
06Distribution
Replica sets with one primary; shards by a shard key, routed by mongos

Why these answers travel together

If one request's data lives in one document, then the document is the natural unit for everything: it's written atomically, it lives on one shard, it loads in one read. Joins and multi-document transactions exist, but cost more, so you shape the data to avoid them.

The exception that proves the axes

Document doesn't mean LSM or a special “NoSQL engine”: MongoDB's collections and indexes are B-trees. Firestore stores its documents in Spanner (archetype A7) and runs serializable transactions across documents.

A4 · DOCUMENT / 17

Archetype A5 of 7 · partitioned key–value & wide-column

Partitioned key–value

The key is the address. Every read and write names a partition key, and the key says which node holds the data. Built for huge, predictable traffic by key: carts, sessions, feeds, events, devices.

DynamoDB
Cassandra
ScyllaDB
Bigtable
HBase
Aerospike
01Model
Key–value or wide-column: a partition key, then a sort key inside it
02Guarantees
Atomic per item or partition; cross-partition transactions small or absent (DynamoDB: 100 items)
03Structure
Mostly LSM (Cassandra, Bigtable, HBase); DynamoDB uses B-trees
04Medium
Disk-first on SSD; Aerospike: index in RAM, records on SSD
05Architecture
Shared-nothing; Bigtable and HBase use a shared file system
06Distribution
Partitioned + replicated: leaderless (Cassandra) or a leader per partition (DynamoDB)

Why these answers travel together

Two lineages. Dynamo (2007) hashes keys onto a ring and writes to any replicas (Riak, ScyllaDB). Bigtable (2006) sorts keys into ranges, one server each (HBase). Cassandra mixes Dynamo's ring with Bigtable's data model. Either way the key is the address: a request by key touches one node, and a query without it must scan.

The exception that proves the axes

Wide-column ≠ columnar: Cassandra and Bigtable keep each row's cells together, a row layout. And partitioned ≠ LSM or leaderless: DynamoDB stores each replica in a B-tree and elects a leader per partition with Multi-Paxos. It shares a name with the Dynamo paper, not its design.

A5 · PARTITIONED KEY–VALUE / 18

Archetype A6 of 7 · shared-storage SQL

Shared-storage SQL

Keep the engine, replace the disk. Postgres, MySQL or SQL Server over a replicated storage service. The SQL, the planner and the B-tree pages stay; durability, replicas and backups move into storage.

AuroraPostgres · MySQL
NeonPostgres
AlloyDBPostgres
Azure SQL HyperscaleSQL Server
01Model
Relational; wire-compatible with Postgres, MySQL or SQL Server
02Guarantees
The engine's own: multi-table ACID, same default isolation
03Structure
B-tree pages, rebuilt by storage from the log
04Medium
Disk-first; storage spread over many machines
05Architecture
Shared storage: one writer, many readers, one volume
06Distribution
Storage replicated (Aurora: 6 copies in 3 zones, 4 to commit); writes not partitioned

Why these answers travel together

The writer sends only log records, and storage builds the pages (Aurora's “the log is the database”). Network traffic stays small, and readers share the same volume, so a new replica or a failover copies no data. But there is still one writer: writes scale up, not out.

The exception that proves the axes

That one-writer ceiling is why AWS added partitioning on top: Aurora Limitless shards across writers, and Aurora DSQL is a distributed SQL design (A7). Shared storage isn't SQL-only either: Bigtable servers keep their files on Colossus.

A6 · SHARED-STORAGE SQL / 19

Archetype A7 of 7 · distributed SQL (NewSQL)

Distributed SQL

ACID across many nodes. Cut the data into key ranges, replicate each range with consensus, and let any node serve SQL. Called NewSQL in the 2010s; now the usual way to scale SQL writes out.

SpannerTrueTime
CockroachDBPostgres wire · Pebble

Transactions across nodes: Serializable (CockroachDB) up to strict serializable (Spanner)

Why these answers travel together

Cross-partition transactions need consensus per range (one agreed history each) and a shared clock (TrueTime, hybrid clocks, a timestamp oracle) so ranges agree on commit order. Ranges are slices of one sorted key space, so an ordered key–value engine below makes them cheap to split and move.

The exception that proves the axes

Transactional SQL doesn't need a B-tree: most of these run on LSM engines. And the layering varies: Aurora DSQL splits SQL, conflict checks, the commit journal and storage into separate services, with optimistic concurrency.

TiDB / 21

Payoff

So which properties actually relate?

A few answers genuinely pull others along, each for a mechanical reason. Everything else is habit or marketing.

Real dependencies, and why

  • OLTP ⇒ rows, OLAP ⇒ columns: a query reads whole records or a few columns.
  • Write-heavy ingest ⇒ LSM: sequential appends beat random page writes.
  • Memory-first ⇒ no pages: hash tables and skiplists; durability from snapshots, logs, replicas.
  • Partitioned ⇒ access by key: a query without the partition key must ask every node.
  • Cross-partition ACID ⇒ consensus + a time source: Raft/Paxos per range, plus TrueTime, hybrid clocks or a timestamp oracle.
  • Single server ⇒ cheap strong transactions: no network inside a commit.

Independent (the myths)

  • Relational ≠ B-tree: CockroachDB and TiDB are SQL on LSM.
  • SQL ≠ single node: Spanner is global SQL.
  • NoSQL ≠ LSM: MongoDB and DynamoDB use B-trees.
  • Document ≠ no transactions: MongoDB and Firestore run multi-document ones.
  • Wide-column ≠ columnar: it's a row layout.
  • In-memory ≠ key–value: VoltDB is relational.
  • Shared storage ≠ new engine: Aurora still uses B-tree pages.

Name the point on each axis, not the brand's marketing word.
