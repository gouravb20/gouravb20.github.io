DATABASES / 01

The root question · workload

Start with the workload. It picks the layout.

What does a typical query touch: a few whole records, or a few columns of millions of records?

OLTP · online transaction processing

Many small reads and writes by key, from users, in milliseconds: “load order 2”, “add item to cart”. Each query wants a whole record, so a record's fields are stored together: a row layout.

page → [1 Ana NYC 30] [2 Bo SF 12] [3 Cy LA 7]
get order 2 → read one page
row layout · this deck

OLAP · online analytical processing

Few big queries from analysts, scanning millions of rows: “revenue by city this year”. Each query wants a few columns, so each column is stored (and compressed) on its own: a column layout.

id → 1 2 3  · name → Ana Bo Cy
city → NYC SF LA · total → 30 12 7
sum(total) → read one column
column layout · Part 4

HTAP systems serve both, usually as a row store plus a columnar copy (TiDB with TiFlash). Specialized workloads (search, time-series, vectors, graphs) get their own engines in Part 4.

Watch the wording: “wide-column” (Cassandra, Bigtable) is not “columnar”. Wide-column stores keep a row's cells together (Bigtable and HBase per column family), so they use a row layout with a flexible set of columns.

THE MAP / 03

Why the axes are independent

Each layer hides the one below it

Codd's 1970 relational paper argued that applications must not depend on how data is organized inside the machine. The ANSI/SPARC model of the mid-1970s named the levels: what users see, the logical schema, the physical storage. Deployment adds a fourth level: which machines hold the bytes, and what they share. Each hidden level can be swapped without the others noticing.

Model ⟂ structure

CockroachDB and TiDB are SQL over an LSM. MongoDB is documents over a B-tree.

Structure ⟂ architecture

RocksDB runs embedded, and as TiKV's engine under TiDB's disaggregated SQL tier. Aurora keeps B-tree pages on shared storage.

Model ⟂ architecture

Disaggregated, shared storage: Bigtable (NoSQL) and Aurora (SQL). Shared-nothing: Cassandra (NoSQL) and CockroachDB (SQL).

Same engine, every deployment

InnoDB runs in a single MySQL server, under Aurora MySQL's shared storage, and in each Vitess shard.

And the other parts' axes

Transactions (Part 3) and distribution (Part 2) are mostly independent too. SQLite is serializable in one file; Spanner is strictly serializable across continents.

Mostly independent

Some answers suit each other, so a few combinations recur: the archetypes. The few real dependencies are on slide 20.

INDEPENDENCE / 04

Axis 01 · logical · data model & query

What shape is the data?

Rows in tables, whole documents, values behind keys, or nodes and edges? Asked in SQL, or through an API?

Relational

Rows with typed columns; joins and foreign keys. Asked in SQL.

idnamecity
1AnaNYC

Document

Self-contained JSON-like trees, read and written whole.

{ "_id": 1, "name": "Ana",
  "addr": { "city": "NYC" } }

Key–value

An opaque value behind a key: get, put, delete. The database can't look inside.

user:1 → "…bytes…"

Wide-column

A partition key picks the node; a sort key orders rows inside it. Columns may differ per row.

user#1 │ 2025-01-03 → {…}
user#1 │ 2025-01-07 → {…}

Graph

Vertices and edges with properties; queries walk paths (Cypher, Gremlin). Covered in Part 4.

(Ana)-[:FOLLOWS]->(Bo)

Two sub-questions

Schema: checked by the database on write (relational) or by the app on read (document, key–value).
Query: declarative (SQL says what; the planner picks how) or an API of operations (get, put, find).

What it decidesWhich queries are natural and which hurt (joins, ad-hoc filters, path walks), and how much checking the database does for you.

How to tellThe query language, and the unit of an atomic write: a row, a document, an item. The models converge: Postgres stores JSON; MongoDB has joins.

DATA MODEL / 05

Axis 02 · physical · storage structure

How does a write change the bytes on disk?

Does the engine overwrite data where it lives, or append new versions and merge them later?

B-tree · update in place

  • Walk a sorted tree of pages to the right leaf, change it, write the page back (a write-ahead log makes it crash-safe).
  • Reads: one root-to-leaf path, predictable. Writes: random, and a small change rewrites a whole page.
Postgres · MySQL · SQL Server · Oracle · SQLite · MongoDB · DynamoDB

LSM-tree · append, merge later

  • Buffer writes in a sorted in-memory table, flush it as an immutable sorted file, merge files in the background.
  • Writes: sequential, high throughput. Reads: may check several files; bloom filters skip most.
RocksDB · Cassandra · ScyllaDB · Bigtable · HBase · CockroachDB · TiKV

Also on this axisHeap + indexes (Postgres writes a new row version; VACUUM reclaims the old) · clustered on the key (InnoDB) · copy-on-write B-tree (LMDB) · log + hash index (Bitcask) · hash tables and skiplists (Redis).

What it decidesThe balance of read, write and space amplification. B-trees favour reads; LSM-trees favour writes and usually take less space.

How to tellThe engine's vocabulary: page, vacuum, fill factor point to a B-tree; memtable, SSTable, compaction to an LSM.

Read more: DDIA ch. 3 · Database Internals ch. 2, ch. 6, ch. 7, which frames this axis as three choices: buffering, mutability, ordering.

STORAGE STRUCTURE / 06

Axis 02 · deep dive

How an LSM-Tree works

Log-Structured Merge-Tree: turn random writes into sequential ones, and clean up later.

WAL
every write is appended to a crash-recovery log first.
Memtable
a sorted in-RAM structure (skiplist) absorbs writes.
SSTable
when full, the memtable flushes to an immutable, sorted file on disk.
Compaction
background merge of SSTables into fewer, bigger, sorted levels — drops overwrites & tombstones.
Bloom filter
per-SSTable probabilistic “is the key even here?” to skip files on reads.
Delete
writes a tombstone marker; the value is really removed during compaction.

writes flow down · reads fan across newest → oldest

Trade-off in one line: cheap writes, more work on reads — the mirror image of a B-Tree.

LSM · LIVE / 08

Axis 03 · system · deployment

Where does it run?

A library in your process, one server, or a cluster of machines?

Embedded

A library linked into the app. No server and no network hop; the app's own process reads and writes the file.

SQLite · RocksDB · LMDB · DuckDB

Single server

Clients connect over the network to one server that owns the disk. Scale up; add read replicas, full copies that serve reads and take over on failure.

Postgres · MySQL · SQL Server · Redis

Cluster

Many machines act as one database, so the data must be split (partitioned) and copied (replicated). What the nodes share decides the rest: three architectures.

Cassandra · TiDB · Aurora · Spanner Slide 10 →

What it decidesHow you scale (up or out), what a failover costs, how far apart the copies can live, and who has to operate it.

How to tellThe install guide: a library you link, one server you start, or nodes you join into a cluster.

How a cluster copies and splits its data (replication, partitioning, consensus) is Part 2.

DEPLOYMENT / 09

Axis 03 · system · cluster architecture

In a cluster, what do compute and storage share?

Does the tier that runs the queries also hold a slice of the data? If yes, it's shared-nothing. If no, compute is disaggregated: over storage nodes that each own a slice, or over one shared storage pool.

C1Shared-nothing (integrated compute and storage)

Every node keeps a slice of the data on its own disk and runs the queries on it. A router in front (mongos) doesn't change that.

Buys: work on local data needs no extra hop; one kind of node to deploy.

Costs: compute and storage grow together; rebalancing moves data.

Cassandra · ScyllaDB · MongoDB · CockroachDB · YugabyteDB

C2Disaggregated compute + shared-nothing storage

Stateless query nodes run the queries; separate storage nodes each own a slice of the data.

Buys: query nodes scale apart from storage; workloads can get their own nodes.

Costs: reads cross to storage (pushdown trims them); moving a slice copies it.

TiDB over TiKV (classic) · VictoriaMetrics cluster

C3Disaggregated compute + shared distributed storage

Stateless compute nodes all read one pool of storage that replicates itself.

Buys: new replicas, failover and rebalancing copy no data; compute scales on its own.

Costs: the network to storage is the bottleneck; one writer per volume (Aurora) or synced caches (Oracle RAC).

Aurora · Bigtable · HBase · Neon · AlloyDB · Azure SQL Hyperscale

Where do Spanner and Bigtable go? Both keep their files on Google’s Colossus. Bigtable is disaggregated, shared storage: nodes hold only pointers to tablets, so rebalancing copies no data; a cluster in another zone is a separate, eventually consistent copy. Spanner is a hybrid: shared storage inside a zone (moving a split copies nothing) and shared-nothing across zones (each read-write or read-only replica keeps a full copy). Google’s docs say “shared nothing”: each split has one server per zone.

Landmarks: Stonebraker, “The Case for Shared Nothing” (1986) · Oracle RAC: older shared disk · Aurora (2017) · TiDB (2020)

ARCHETYPES / 11

Archetype A1 of 7 · embedded engine

Embedded engines

The database is a library. No server and no network: the engine runs inside your process and stores to a local file. Phones, browsers, desktop apps, edge devices, and the storage layer of other databases.

SQLiterelational · B-tree
RocksDBkey–value · LSM
LMDBkey–value · copy-on-write
DuckDBthe OLAP cousin
01Model
Relational (SQLite) or key–value (RocksDB, LMDB)
02Structure
B-tree (SQLite), LSM (RocksDB), or copy-on-write B-tree (LMDB)
03Architecture
Embedded: a library in your process that reads and writes a local file; nothing to replicate or partition, by design

Why these answers travel together

No network and no server means nothing to partition or replicate, and one writer at a time (SQLite, LMDB) buys the strongest isolation cheaply. SQLite is fully ACID out of the box; RocksDB syncs its log only when a write asks for it.

The exception that proves the axes

Embedded engines are also the bottom layer of distributed databases: TiKV runs RocksDB, YugabyteDB a fork of it, and CockroachDB's Pebble is modelled on it. rqlite and LiteFS replicate SQLite. The engine stays embedded; a system layer above adds distribution.

A1 · EMBEDDED / 12

Archetype A2 of 7 · classic relational server

Classic relational

One server, strong guarantees. Tables, SQL and ACID transactions, with replicas for reads and failover. The 40-year default, and the reason the axes feel inseparable: these answers almost always ship together.

PostgreSQL
MySQL
MariaDB
SQL Server
Oracle
01Model
Relational + SQL; JSON columns too
02Structure
B-tree. Postgres keeps rows in a heap; InnoDB clusters them on the primary key
03Architecture
Single server: one leader takes every write, plus read replicas; table partitions normally stay on that server

Why these answers travel together

One server owns all the data, so making any set of rows atomic and isolated needs no network round trips and no consensus. That's why transactions, joins and constraints feel like part of “SQL”. The limit is the one server: writes scale up, not out.

The exception that proves the axes

Same engines, other system-layer answers: Citus and Vitess shard Postgres and MySQL across nodes (shared-nothing), Oracle RAC runs several servers over shared disks, and Aurora moves the storage into a shared service (archetype A6).

A2 · CLASSIC RELATIONAL / 13

Archetype A3 of 7 · key–value store

Key–value stores

The key is the main door. Every get, put and delete names a key, and the database finds the value by that key. Caches, sessions, rate limits, leaderboards, feature flags, and the metadata of other systems.

Redisvalues are data structures
ValkeyLinux Foundation fork of Redis
Memcachedplain cache · bytes
Aerospikerecords with named bins
01Model
Key → value. Redis: strings, hashes, lists, sets, sorted sets, streams; Aerospike: records with bins; Memcached: bytes
02Structure
Hash tables and skiplists in RAM (Redis, Memcached); Aerospike: a key index over log-structured storage
03Architecture
Single server (Redis runs one command at a time). Shared-nothing when a hash of the key picks the owner: each Redis Cluster master serves its hash slots, each Aerospike node its partitions; Memcached leaves sharding to the client

Why these answers travel together

If every request names a key, the database needs no query planner, and hashing the key picks the node, so partitioning is trivial and each operation is one small step. The price: queries across keys need an extra index, built in (Redis Search in Redis 8, Aerospike secondary indexes) or kept by the app (a Redis set of IDs, a sorted set for a leaderboard).

The exception that proves the axes

Key–value is also the layer under other models: TiDB's SQL runs on the TiKV key–value store (A7), CockroachDB's SQL on the Pebble engine, and FoundationDB's Record Layer keeps structured records on its ordered keys. A table row becomes a key (table + primary key) with its columns as the value. How consistent a store is, from a cache to etcd, is a Part 2 question.

A3 · KEY–VALUE / 14

Archetype A4 of 7 · document store

Document stores

The record is a tree. Each record is a self-contained JSON-like document (DynamoDB calls it an item), loaded and saved whole. A good fit when data is read together (an order with its lines) and the schema changes often.

MongoDBWiredTiger · B-tree
CouchbaseJSON + key–value API
DynamoDBkey-first · B-tree
Firestorebuilt on Spanner
01Model
JSON-like documents, flexible schema. MongoDB and Firestore query any indexed field; DynamoDB goes by partition + sort key, plus secondary indexes
02Structure
B-tree: MongoDB's WiredTiger, and DynamoDB's storage nodes (a B-tree plus a write-ahead log). Firestore sits on Spanner
03Architecture
Shared-nothing: each MongoDB shard and DynamoDB storage node serves the data it holds; mongos and DynamoDB's request routers only route. Couchbase splits by service: key–value calls go to the Data node that owns the vBucket; SQL++ runs in the Query service, which fetches from Data nodes (disaggregated, shared-nothing storage). Firestore runs on Spanner (per Google's ICDE 2023 paper), so it inherits Spanner's hybrid

Why these answers travel together

If one request's data lives in one document, the document is the natural unit for everything: written atomically, stored on one partition, loaded in one read. DynamoDB takes it furthest: related items share a partition key and come back in one query. Joins and multi-document transactions exist, but cost more, so you shape the data around the reads.

The exception that proves the axes

Document doesn't mean LSM or a special “NoSQL engine”: MongoDB and DynamoDB both store data in B-trees. DynamoDB shares a name with the 2007 Dynamo paper, not its design: each partition elects a leader with Multi-Paxos. And Firestore keeps its documents in Spanner (A7).

A4 · DOCUMENT / 15

Archetype A5 of 7 · wide-column store

Wide-column stores

Sorted rows inside a partition. A partition key picks the node; inside it, rows are sorted by a clustering key, and each row can have its own columns. Built for huge write volumes read back by key and range: events per device, messages per chat, a feed per user.

CassandraCQL · leaderless
ScyllaDBCassandra-compatible, in C++
BigtableGoogle · tablets
HBaseopen-source Bigtable
01Model
Partition key → rows sorted by a clustering key; columns can differ per row; no joins
02Structure
LSM in all four: memtable, SSTables, compaction (the Bigtable paper named them)
03Architecture
Shared-nothing, no leader: Cassandra (a hash ring) and ScyllaDB (hash-split tablets) nodes serve the ranges they store. Disaggregated, shared storage: Bigtable and HBase serve each key range from one server, but the range's files sit on Colossus or HDFS, so a range moves without copying data

Why these answers travel together

Two lineages. Bigtable (2006) gave the data model and the LSM engine. Dynamo (2007) gave the hash ring and leaderless replication. Cassandra combines both. Heavy writes suit an LSM, and a request by partition key touches one node; a query without it must scan the cluster.

The exception that proves the axes

Wide-column ≠ columnar: Cassandra keeps a row's cells together, Bigtable and HBase keep them together per column family; none stores one column across rows. Columnar storage is Part 4. And one model runs on two architectures: Cassandra is shared-nothing, while Bigtable and HBase run on disaggregated, shared storage (Colossus, HDFS).

A5 · WIDE-COLUMN / 16

Archetype A6 of 7 · shared-storage SQL

Shared-storage SQL

Keep the engine, replace the disk. Postgres, MySQL or SQL Server over a replicated storage service. The SQL, the planner and the B-tree pages stay; durability, replicas and backups move into storage.

AuroraPostgres · MySQL
NeonPostgres
AlloyDBPostgres
Azure SQL HyperscaleSQL Server
01Model
Relational; wire-compatible with Postgres, MySQL or SQL Server
02Structure
B-tree pages, rebuilt by storage from the log
03Architecture
Disaggregated, shared storage, one writer per volume: Aurora's writer and up to 15 readers mount one volume, which storage keeps as 6 copies across 3 zones

Why these answers travel together

The writer sends only log records, and storage builds the pages (Aurora's “the log is the database”). Network traffic stays small, and readers share the same volume, so a new replica or a failover copies no data. But there is still one writer: writes scale up, not out.

The exception that proves the axes

That one-writer ceiling is why AWS added partitioning on top: Aurora Limitless shards across writers, and Aurora DSQL is a distributed SQL design (A7). Disaggregated, shared storage isn't SQL-only either: Bigtable servers keep their files on Colossus.

A6 · SHARED-STORAGE SQL / 17

Archetype A7 of 7 · distributed SQL (NewSQL)

Distributed SQL

ACID across many nodes. Cut the data into key ranges, replicate each range with consensus, and let any node serve SQL. Called NewSQL in the 2010s; now a common way to scale SQL writes out.

SpannerTrueTime
CockroachDBPostgres wire · Pebble
TiDBMySQL wire · TiKV
YugabyteDBPostgres · DocDB
Aurora DSQLPostgres-compatible
01Model
Relational; Postgres- or MySQL-compatible SQL
02Structure
LSM: Pebble, RocksDB; Spanner's Ressi format is LSM-style
03Architecture
Shared-nothing: every node of a single-tenant CockroachDB cluster, and every YugabyteDB node, runs SQL and stores Raft-replicated ranges. Disaggregated, shared-nothing storage: stateless TiDB servers over TiKV (classic TiDB); Aurora DSQL is similar, plus a shared commit journal. Spanner is a hybrid (slide 10)

Why these answers travel together

Transactions across ranges need consensus per range (one agreed history each) and a shared clock (TrueTime, hybrid clocks, a timestamp oracle) so ranges agree on commit order. Ranges are slices of one sorted key space, so an ordered key–value engine below makes them cheap to split and move.

The exception that proves the axes

Transactional SQL doesn't need a B-tree: most of these run on LSM engines. And the layering varies: Aurora DSQL splits SQL, conflict checks, the commit journal and storage into separate services, with optimistic concurrency.

A7 · DISTRIBUTED SQL / 18

Archetype A7 · case study

Case study: TiDB

One system where the axes are separate parts you can point at: SQL, storage engine, placement and an analytics copy. It is the canonical disaggregated, shared-nothing storage design (classic TiDB): stateless TiDB servers over TiKV nodes that each own their Regions.

  • TiDB: stateless SQL layer (MySQL-compatible). Pure compute; scale it out freely.
  • TiKV: distributed KV storage on RocksDB (LSM). Each node owns Regions (key ranges), each a Raft group; moving a Region copies its data (classic TiDB; TiDB Cloud's TiDB X keeps the data in object storage, so adding a TiKV node moves no data).
  • PD (Placement Driver): the brain, holding metadata, data placement and timestamps.
  • TiFlash: a columnar replica for analytics → HTAP in one system (the bridge to Part 4).

TiDB / 19

Payoff

So which properties actually relate?

A few answers genuinely pull others along, each for a mechanical reason. Everything else is habit or marketing.

Real dependencies, and why

  • OLTP ⇒ rows, OLAP ⇒ columns: a query reads whole records or a few columns.
  • Write-heavy ingest ⇒ LSM: sequential appends beat random page writes.
  • Shared-nothing storage (C1 and C2) ⇒ partition by key: a query without the key asks every storage node.
  • Ranges that split and move ⇒ an ordered key–value engine underneath: a range is a slice of one sorted key space, so splitting it is cheap.
  • Shared storage (C3) ⇒ writers must coordinate: most designs give each piece of data one owner (Aurora: one writer for the whole volume, so writes scale up, not out; Bigtable: one server per tablet). Oracle RAC lets every instance write and keeps their caches in sync with Cache Fusion.
  • Disaggregated compute ⇒ query nodes scale apart from storage, but data they don't cache crosses the network.

Independent (the myths)

  • Relational ≠ B-tree: CockroachDB and TiDB are SQL on LSM.
  • SQL ≠ single node: Spanner and CockroachDB spread SQL across many nodes.
  • NoSQL ≠ LSM: MongoDB and DynamoDB use B-trees.
  • Wide-column ≠ columnar: it's a row layout.
  • Shared storage ≠ new engine: Aurora still uses B-tree pages.
  • NoSQL ≠ shared-nothing: Bigtable runs on disaggregated, shared storage.

Name the point on each axis, not the brand's marketing word.
