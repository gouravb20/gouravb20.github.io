Specialized databases:
when the query shape decides.

Some questions fit neither a B-Tree nor a column scan: find the nearest vectors, roll up a time window, follow edges for several hops, rank documents by relevance. Each family exists both inside PostgreSQL, as an extension or a built-in feature, and as a separate engine built around that one query shape.

Four query shapes general engines handle badly

A B-Tree answers “equal to” and “between”. These four questions ask something else, so a general-purpose engine falls back to full scans or chains of joins.

FOUR QUERY SHAPES / 02

Vector databases · 1 of 5

Searching by meaning, not by value

  • Embeddings: a model turns text, images or audio into a vector of a few hundred to a few thousand floats (commonly 384–3072). Similar meaning → nearby vectors.
  • The query is “nearest neighbours”: embed the question, return the k closest stored vectors. No exact match, no WHERE; results are ranked by distance.
  • Distance metric: cosine (angle), dot product (equals cosine on normalized vectors) or Euclidean L2; pgvector also has L1, plus Hamming and Jaccard for binary vectors. Use the one your embedding model was trained for.
  • Why B-Trees don't help: they order data along one key; “closest in 768 dimensions” has no sort order. Space-partitioning trees (k-d trees) degrade toward brute force as dimensions grow.
  • Brute force is O(N·d): 10M vectors × 768 dims ≈ 7.7 billion multiply-adds per query, over about 31 GB of raw floats (4 bytes per dimension). Hence approximate nearest-neighbour (ANN) indexes.

Vector databases · 2 of 5

ANN indexes trade recall for speed

Every index below has a knob that trades recall (did we find the true nearest neighbours?) against latency and memory.

Measure, don't assume: compute recall@k against brute force on a sample of your own queries before picking settings.

VECTORS · INDEXES / 04

Vector databases · 3 of 5

HNSW: a skip list made of graphs

Hierarchical Navigable Small World (Malkov & Yashunin, 2016): an ANN index offered by pgvector, Milvus, Qdrant (its only dense index) and Weaviate (the default).

  • Small-world graph: each vector links to its nearest neighbours, so hopping toward the query reaches the right region in a few steps.
  • Layers: every vector is on L0; each also appears higher up with exponentially falling probability, like a skip list (the paper's own analogy). Upper layers are sparse express lanes.
  • Search: hop greedily from the top entry point until no neighbour is closer, then drop a layer. On L0, keep the efSearch best candidates; return the top k.
  • Insert: draw the vector's top layer at random, find neighbours with the same search (efConstruction), link to M per layer, prune over-full neighbours.
  • Costs: graph and vectors usually live in RAM; deletes leave tombstones; heavy filters can disconnect the graph.

The hard part is filtering

WHERE tenant = 7 plus nearest-neighbour. Post-filtering can return fewer than k: in pgvector, a filter matching 10% of rows with hnsw.ef_search = 40 leaves about 4 (iterative index scans, 0.8.0+, keep going). Pre-filtering can break HNSW's graph connectivity; Qdrant adds payload edges, Pinecone filters before ranking. Test with your real filters.

Rule of thumb

Already on Postgres with up to a few million vectors: start with pgvector. Very large collections, heavy filtering or strict latency at high QPS: evaluate a dedicated engine.

VECTORS · LANDSCAPE / 07

Time-series · storage tricks

Append-mostly data indexed by time

Workload traits

Writes are almost all appends at “now”; reads are recent windows and rollups; old data is rarely edited and usually expires. Model: (metric, labels, timestamp, value).

Cardinality is the real enemy. Every unique label combination is a separate series; a label like user_id can multiply series until memory and index size blow up. Prometheus's advice: never put user IDs or email addresses in labels.

Standard techniques

Time partitioning into chunks, so expiry is “drop a chunk” (Prometheus: two-hour blocks, recent samples guarded by a write-ahead log). Downsampling / rollups for old data (1s → 1m → 1h). Retention policies as first-class config. Row, then column: TimescaleDB's hypercore turns older chunks into a compressed columnstore. Specialized compression, below.

// delta-of-delta timestamps (Facebook's Gorilla, VLDB 2015: about 96% of timestamps fit in one bit) timestamps : 1000 1060 1120 1180 1241 deltas : 60 60 60 61 delta-of-delta : 0 0 1 ← regular scrapes become mostly zeros → a few bits each // float values: XOR with the previous value; similar values share leading/trailing zero bits v[n] XOR v[n-1] → store only the meaningful middle bits // together: 1.37 bytes per (timestamp, value) point on average, about 12× smaller

Regular intervals and slowly changing values are what make these encodings effective; noisy, irregular data compresses much worse.

TIME-SERIES · LANDSCAPE / 09

Graph · model & query

Graphs: property graphs, RDF and GQL

  • Property graph: nodes and edges both carry a label and properties, so an edge can hold its own data (since: 2019). Neo4j, Amazon Neptune, Spanner Graph, Apache AGE.
  • RDF: a graph is a set of triples (subject, predicate, object) named by IRIs. SPARQL, the W3C query language, matches triple patterns, required and optional.
  • GQL (ISO/IEC 39075:2024): the ISO query language for property graphs. Neo4j's Cypher (open spec: openCypher) was a key inspiration, and Cypher supports most mandatory GQL features.
  • SQL/PGQ (ISO/IEC 9075-16:2023): define a property graph over existing tables and match paths with GRAPH_TABLE, inside SQL. Same pattern-matching core as GQL. Oracle AI Database 26ai, Spanner Graph.
  • Gremlin (Apache TinkerPop): a chain of steps, g.V().out('knows'), instead of a pattern. Neptune speaks Gremlin, openCypher and SPARQL.

GRAPH · MODEL / 10

Graph · storage & traversal

Why a traversal is cheap in a graph engine

Index-free adjacency (Neo4j): each node record leads straight to its relationships, so a hop follows a stored link instead of searching an index. Not every graph database works this way; three ways to store the same graph:

Supernodes

A vertex with thousands of edges makes every hop through it slow. Neo4j keeps a dense node's relationships in a B+ tree under their own root; JanusGraph can split one huge vertex across machines (a vertex cut).

Cut edges

An edge whose two ends live on different machines is a cut edge: each traversal across it is a network round trip. JanusGraph places vertices at random by default; on 4 machines that cuts about 3 edges in 4.

Scale reads, not the graph

Amazon Neptune stores edges and properties as quads; one writer and up to 15 read replicas share one cluster volume (disaggregated, shared storage). Neo4j's Infinigraph (2025.12) shards properties but keeps every node and relationship in one graph shard.

GRAPH · STORAGE / 11

Search · inverted index

Search engines: inverted indexes and BM25

BM25 ranking

The default in Lucene since 6.0 and in Elasticsearch since 5.0 (2016), replacing TF‑IDF. k1 = 1.2 limits how much repeating a term helps; b = 0.75 normalizes for document length. PostgreSQL's ts_rank uses no corpus-wide statistics, so it is not BM25.

Near-real-time

A new document becomes searchable at the next refresh, which writes the in-memory buffer out as a new segment: every 1 s by default (5 s on Elastic Serverless), and only on indices searched in the last 30 s.

Segments, like an LSM-Tree

Segments never change once written; a delete only marks a document, and merges reclaim the space: Part 1's LSM-Tree in another form. Not a system of record: keep the source of truth elsewhere and reindex from it.

Search · landscape & hybrid search

Search engines, and hybrid search

Hybrid search runs a keyword query (BM25) and a vector query (kNN, Slide 03), then merges the ranked lists. Reciprocal rank fusion (Cormack, Clarke, Büttcher, SIGIR 2009) uses only ranks: Σ 1/(k + rank), k = 60.

CHEAT SHEET / 14

Summary · end of the series

What to remember.

Vectors need ANN

Brute force is exact but O(N·d). HNSW is a skip list of graphs; efSearch trades recall for latency. Test with your real filters.

Time is the index

Partition by time, compress with delta-of-delta and XOR, expire by dropping chunks. Watch label cardinality.

Edges, not joins

A hop should read a node's stored edges, not run a join. Supernodes and cut edges are the price; GQL and SQL/PGQ share one pattern language.

Search inverts text

Term → documents, ranked with BM25, in immutable segments merged in the background. Add vectors with RRF for hybrid search.

Specialize deliberately: start from the dominant query shape, try the PostgreSQL extension first, and move to a dedicated engine when scale, filtering or latency demand it.
