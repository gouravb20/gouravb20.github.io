DATABASES / 01

Scoping today

Databases split into OLTP vs. OLAP

Databases are generally divided by workload. Today we look at OLTP, row-oriented databases only.

Workload · OLTP vs OLAP

OLTP — many small reads/writes, point lookups, strict consistency. Your app's live database.

OLAP — few huge scans, aggregates over billions of rows. Warehouses & analytics.

OLTP — todayOLAP — Part 2

Layout · Row vs Columnar

Row-oriented stores a whole record together — great for “fetch this user”.

Columnar stores each column together — great for “average this column over 1B rows”. It is an OLAP technique.

row — todaycolumnar — Part 2

Watch the wording: “wide-column” (Cassandra, Bigtable) is not “columnar”. Wide-column is still row-oriented storage — we'll hit that trap head-on later.

THE 4 AXES / 03

The one idea to keep

The axes are (mostly) orthogonal

Pick any combination. Real systems prove almost every box can be ticked independently.

Model ⟂ Engine

Relational doesn't imply B-Tree. CockroachDB is full SQL built on an LSM engine.

Engine ⟂ Topology

The same B-Tree or LSM engine runs on one laptop or across 500 nodes. Distribution is a layer above.

Model ⟂ Architecture

Bigtable is NoSQL and separates compute (tablet servers) from storage (Colossus).

SQL ⟂ Scale

Google Spanner gives you SQL + ACID across continents. “SQL” never meant “single node”.

Architecture ⟂ Engine

Aurora splits compute from storage yet still uses B-Tree pages. Disaggregation says nothing about the engine.

So… what clusters?

A handful of archetypes recur because certain choices reinforce each other. The rest of the talk is a tour of them.

DATA MODELS / 05

Axis 02 · storage engine

B-Tree vs. LSM-Tree

How the engine physically places and finds rows. This is the single most under-appreciated axis.

B-Tree

  • Update in place — find the page, overwrite it.
  • Balanced tree of pages; read-optimized, predictable point lookups.
  • Random writes → write amplification under heavy load.
  • The default for relational & OLTP for 40 years.

Sorted pages · O(log n) to any key

LSM-Tree

  • Never overwrite — buffer writes in RAM, flush as sorted files.
  • Sequential writes → huge write throughput.
  • Reads may touch several files; bloom filters + compaction keep it fast.
  • The engine behind most big-data / write-heavy stores.

Append-only · merge later

STORAGE ENGINE / 06

Axis 03 · architecture

Separating compute from storage

The cloud-native move: let the query engines and the data layer scale — and fail — independently.

  • Coupled — CPU and disk live on the same node. Scale one, you pay for both.
  • Disaggregated — stateless compute talks to a shared, replicated storage service over the network.
  • Add read replicas in seconds; storage grows on its own; compute can scale to zero.
  • Amazon Aurora, Neon, Spanner, TiDB, Snowflake (OLAP).

Note: classic Aurora disaggregates storage but still uses B-Tree pages — architecture ⟂ engine, again.

scale the two sides on their own curves

ARCHITECTURE / 07

Axis 04 · topology

Single-node vs. distributed

  • Single-node — one machine owns all the data. Simple, strongly consistent, limited by one box. Postgres, MySQL, SQLite.
  • Distributed — data is sharded (split by key) and replicated (copied for safety) across many nodes.
  • Buys horizontal scale + fault tolerance — pays in consensus (Raft/Paxos), clock skew, and the CAP trade-offs.
  • Orthogonal to everything else: any model, any engine can be distributed.

shard for scale · replicate for safety

TRADITIONAL SQL / 10

The tour · archetype 3

Document databases

Flexible JSON records, high throughput, horizontal scale — and B-Trees quietly doing the indexing.

MongoDBWiredTiger · B-Tree
DynamoDBWAL + B-Tree per replica
Firestorebuilt on Spanner
  • Model is document / flexible schema — but the indexes are classic B-Trees. Model ⟂ engine once more.
  • MongoDB's WiredTiger engine is B-Tree by default. DynamoDB (per the 2022 paper) is a write-ahead log plus a B-Tree per partition replica.
  • Firestore runs on Google's Spanner infrastructure — its indexes are Spanner tables.

Takeaway: “NoSQL / document” tells you about the API & schema, almost nothing about the storage engine.

DOCUMENT / 11

The tour · archetype 4 · into big-data

Wide-column, on LSM

Built for relentless write throughput and append-heavy, massive-scale workloads — the gateway to data engineering.

Bigtablethe 2006 original
Cassandramasterless · AP
ScyllaDBC++ Cassandra, shard-per-core
HBaseBigtable on Hadoop
  • Why they exist: ingest firehoses — events, metrics, IoT, feeds — at a scale single-node SQL can't touch.
  • Keyed by partition + clustering key; data sorted on disk by that key — the sort order is the primary index.
  • RocksDB is the embedded LSM key-value engine these ideas spawned — it powers TiKV & others (CockroachDB uses its cousin, Pebble). It's an engine, not a wide-column DB itself.

The trap again: wide-column ≠ columnar. Cassandra & Bigtable store each row's cells together (row-oriented). “Columnar” is an OLAP layout — Part 2.

WIDE-COLUMN / 12

Deep dive

How an LSM-Tree works

Log-Structured Merge-Tree: turn random writes into sequential ones, and clean up later.

WAL
every write is appended to a crash-recovery log first.
Memtable
a sorted in-RAM structure (skiplist) absorbs writes.
SSTable
when full, the memtable flushes to an immutable, sorted file on disk.
Compaction
background merge of SSTables into fewer, bigger, sorted levels — drops overwrites & tombstones.
Bloom filter
per-SSTable probabilistic “is the key even here?” to skip files on reads.
Delete
writes a tombstone marker; the value is really removed during compaction.

writes flow down · reads fan across newest → oldest

Trade-off in one line: cheap writes, more work on reads — the mirror image of a B-Tree.

LSM · LIVE / 14

The tour · archetype 5

Distributed SQL at scale

Full SQL + ACID transactions, but sharded and replicated across the planet.

Google SpannerTrueTime · external consistency
Aurora DSQLdisaggregated · Postgres-compatible
CockroachDBPostgres wire · LSM engine
  • Spanner — SQL + ACID globally; storage descends from Bigtable on Colossus (an LSM-style format, Ressi, per the 2017 SIGMOD paper).
  • Aurora DSQL — disaggregated query processors, journal & storage; optimistic concurrency; scales reads & writes independently.
  • CockroachDB — shared-nothing distributed SQL, built on an LSM engine (Pebble) with Raft.

Myth-buster: “transactional SQL” does not require a B-Tree. Two of these three are LSM underneath.

DISTRIBUTED SQL / 15

The convergence · 1 of 2

NewSQL

What happens when you want the SQL + ACID of the 1980s at the scale of the 2010s.

The pitch

Keep the relational model, SQL, and real transactions — but make the system distributed, elastic, and fault-tolerant like a NoSQL store.

How they're built

Distributed consensus (Raft/Paxos) over an LSM key-value layer, usually with compute separated from storage. Several axes flip at once.

Google SpannerTrueTime · external consistency
CockroachDBPostgres wire · LSM engine
TiDBMySQL wire · TiKV on RocksDB
Relational + SQLDistributedLSM engineCompute ⁄ storage splitOLTP (often HTAP)

Examples: Google Spanner, CockroachDB, TiDB. This is the clearest proof that the four axes really are independent — NewSQL remixes them deliberately.

TiDB / 17

Payoff

So which properties actually relate?

Genuinely correlated

  • OLAP ⇒ columnar storage (analytics scans columns).
  • OLTP ⇒ row-oriented (fetch whole records).
  • Write-heavy / big-data ⇒ LSM (sequential writes win).
  • In-memory KV ⇒ hash/skiplist, no B-Tree/LSM.
  • Global scale ⇒ distributed + compute/storage split.

Independent (the myths)

  • Relational ≠ B-Tree — CockroachDB is SQL on LSM.
  • SQL ≠ single-node — Spanner is global SQL.
  • Document ≠ no index — Mongo/Dynamo use B-Trees.
  • Wide-column ≠ columnar — it's row-oriented.
  • Distributed ≠ NoSQL — NewSQL is distributed SQL.
  • Disaggregated ≠ new engine — Aurora splits compute from storage, still B-Tree pages.

Name the point on each axis — not the brand's marketing word.
